## 한눈에 보기

모바일 앱 보안은 휴대전화 앱이 사용자의 기기에 설치되고, 서비스 서버와 정보를 주고받으며, 여러 운영체제와 앱 버전에서 계속 작동하는 상황을 다룬다. 웹과 같은 계정 기능을 제공해도 앱은 사용자가 업데이트하기 전까지 이전 버전으로 남을 수 있다. 그래서 출시 전에 확인한 위험뿐 아니라 **이미 배포된 앱에서 문제를 발견했을 때 누구에게 어떤 버전의 수정을 전달할지**도 중요한 일이다. 회사 지급 휴대전화의 등록·분실 대응·운영체제 갱신처럼 기기 자체를 관리하는 일은 [엔드포인트 보안](/fields/endpoint/)의 책임과 구분해 읽어야 한다.

모바일 앱 보안 담당자가 모두 앱을 직접 개발하거나 연구하는 것은 아니다. 어떤 조직은 새 기능의 검토와 출시 판단에, 어떤 조직은 여러 앱의 공통 보호 기준에, 어떤 조직은 취약점 연구와 제품팀 협업에 무게를 둔다. 공고의 직함보다 실제 담당 앱과 개발팀의 관계를 읽어야 한다.

## 현장의 업무와 결과물

앱에 새로운 로그인 기능이 들어간다고 해 보자. 담당자는 사용자가 어떤 기기에서 어떤 흐름을 거치는지, 앱과 서버가 각각 무엇을 결정하는지, 이전 버전 사용자는 어떻게 안내받는지 제품·개발팀과 확인한다. 변경 전에 검토할 질문을 정하고, 발견 사항이 있으면 영향받는 앱·운영체제·버전을 분리해 전달한다. 수정된 빌드가 나왔을 때는 같은 조건에서 다시 확인하고, 고객 지원팀이 이용자에게 설명해야 할 제한이 있는지도 점검한다.

결과물에는 앱 버전별 위험 평가, 재현 가능한 발견 기록, 보호 기능 요구, 수정 후 확인 결과, 출시·업데이트 결정에 필요한 남은 질문이 포함될 수 있다. 단순히 문제가 '있다'고 적는 보고서보다 **어느 버전과 사용자에게 어떤 조치가 필요한지**를 알 수 있는 기록이 유용하다. 실제 운영 정보나 타인의 앱은 소유자의 허가 없이 시험하지 않는다.

## 세부 갈래

- **모바일 앱 개발 협업:** 기능을 만들고 고칠 때 제품팀과 위험을 검토한다. 앱과 서버의 책임을 나누고 개발자가 적용할 요구와 확인 기준을 남긴다.
- **기기·운영체제 환경:** 앱이 다양한 기기와 운영체제 버전에서 사용된다는 제약을 다룬다. 특정 환경에서만 관찰되는 문제라면 확인한 범위와 아직 모르는 범위를 구분한다.
- **출시와 업데이트:** 수정된 앱을 내놓는 시점, 이전 버전 사용자, 긴급 수정과 정상 출시 일정의 관계를 살핀다. 실제 배포 결정권이 보안팀에 있는지는 조직마다 다르다.
- **모바일 연구와 보호 기능:** 일부 자리는 새로운 문제를 조사하거나 앱 보호 기능을 직접 개발한다. 출시 검토 담당자에게 그 전문 연구·구현 업무를 자동으로 요구해서는 안 된다.

## 직무와 협업의 차이

[모바일 보안 엔지니어](/careers/mobile-security-engineer/)는 모바일 서비스의 출시와 업데이트 전반에서 위험 평가와 적용 결과를 연결하는 직접적인 직무다. [애플리케이션 보안 엔지니어](/careers/application-security-engineer/)는 모바일을 포함한 여러 서비스의 개발 흐름을 맡을 수 있지만, 공고가 웹·API 중심일 수도 있다. [제품 보안 엔지니어](/careers/product-security-engineer/)는 앱을 제품의 한 부분으로 보며 배포 뒤 제보와 고객 영향까지 조정할 수 있다. 세 역할은 겹치지만 같은 직함이나 요구 경력을 뜻하지 않는다.

모바일 개발자는 구현과 기기별 제약을, 서버 개발자는 뒤에서 처리하는 권한과 정보 흐름을, 제품팀은 사용자 경험과 출시 일정을 제공한다. 고객 지원은 이미 배포된 버전의 문제를 사용자에게 설명할 때 필요하다. 이 관계를 조율한 기록도 직무 성과다.

## 입문과 채용 공고

앱 개발·품질 검증·웹 애플리케이션 보안 경험에서 시작할 수 있다. 본인이 만든 공개 가능한 앱 한 기능을 대상으로 사용자 흐름, 다루는 정보, 변경 전후 앱 버전, 확인 결과와 미확인 조건을 요약해 보자. 실제 서비스 경험이라면 공개할 수 없는 고객 정보와 기기 자료를 익명화한다. 포트폴리오의 핵심은 기술 이름을 늘어놓는 것이 아니라 **문제 발견이 수정·출시 판단과 어떻게 이어졌는지**다.

공고에서는 담당이 Android·iOS 앱 모두인지, 연구·앱 보호 기능 개발인지, 출시 검토·조정인지, 몇 개 앱을 지원하는지 확인한다. [토스의 모바일보안 연구 공고](https://toss.im/career/job-detail?job_id=7780944003)는 모바일 점검과 보호 기능을 함께 제시했고, [쿠팡의 모바일 보안 공고](https://www.coupang.jobs/kr/jobs/8203471/senior-staff-security-engineer-mobile-security-digital-trust/)는 여러 앱에 공통 기준을 적용하는 경력 자리의 사례다. 두 사례의 연차나 기술 조건을 모든 모바일 보안 직무의 공통 자격으로 옮기지 않는다. 개발·검증을 잇는 넓은 기준은 [NIST의 안전한 소프트웨어 개발 프레임워크](https://csrc.nist.gov/pubs/sp/800/218/final)에서 확인할 수 있지만, 이 기준이 모바일 채용 직함을 정하는 것은 아니다.

모바일 앱이 호출하는 서비스의 기능·권한은 [웹·애플리케이션 보안](/fields/web/), 앱에서 다루는 개인정보의 수집·이용 책임은 [데이터 보안](/fields/data/)과 연결된다. 기기 안의 펌웨어와 장기간 지원되는 연결 장치는 [IoT·임베디드 보안](/fields/iot-embedded/)에서 다룬다.
