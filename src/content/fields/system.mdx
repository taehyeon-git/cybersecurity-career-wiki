## 처음 보는 사람을 위한 설명

시스템·서버 보안은 회사의 서비스나 내부 업무가 돌아가는 **컴퓨터 환경**을 보호하는 일이다. 여기서 시스템은 사무실의 물리 서버만 뜻하지 않는다. 운영체제, 가상 서버, 관리용 서버, 서비스가 사용하는 실행 환경도 포함된다. 서비스가 잘 작동하는지 보는 일반 운영과 가까이 일하지만, 보안 담당자는 누가 관리할 수 있는지, 새 시스템이 보호 범위에서 빠지지 않았는지, 변경 뒤 위험이 늘어나지 않았는지를 특히 확인한다.

처음에는 “서버를 지키는 한 가지 직업”으로 생각하기 쉽다. 실제 채용에서는 시스템 보안 엔지니어, 인프라 보안 담당자, 보안 아키텍트, 진단 담당자처럼 **같은 대상을 다른 책임으로 다루는 직무**가 있다. 한 회사는 여러 책임을 한 자리에 묶고, 다른 회사는 운영·진단·설계를 서로 다른 팀에 둔다.

## 실제 하루와 판단

예를 들어 새 서비스의 서버가 추가된다. 보안 담당자는 운영팀에 소유자와 사용 목적, 관리 책임자를 확인한다. 기존 접근 기준과 점검 대상에 들어가는지 보고, 빠진 항목은 누가 언제 처리할지 정한다. 변경이 정상 서비스에 미칠 영향이 크면 운영 시간과 되돌릴 조건도 함께 논의한다. 완료 뒤에는 적용 여부와 남은 예외를 기록해 다음 담당자가 이어받게 한다.

이 분야의 질문은 “서버에 보안 도구가 설치됐는가”에서 끝나지 않는다. **어떤 시스템이 존재하고 누가 책임지는가**, 관리 권한이 필요한 사람에게만 주어졌는가, 오래된 예외를 누가 재검토하는가, 장애와 보안 위험이 충돌할 때 누가 결정하는가가 중요하다. [NIST Cybersecurity Framework](https://www.nist.gov/cyberframework)는 자산 파악과 보호를 위험 관리의 일부로 다루지만, 이 위키의 분야 이름을 공식 직무명으로 지정하지는 않는다.

## 일하는 환경과 세부 갈래

- **내부 업무 시스템:** 직원 계정과 공용 서버, 관리용 장비를 담당하는 IT 운영팀과 일한다. 새 시스템 등록, 관리 권한 변경, 퇴역한 시스템의 정리가 실제 업무에 포함될 수 있다.
- **서비스 운영 서버:** 고객에게 제공하는 서비스의 변경 일정과 가용성을 고려한다. 보안 기준을 적용하면서도 서비스 중단·성능 문제를 함께 판단하고 운영·개발팀에 변경 결과를 인계한다.
- **가상화·혼합 환경:** 같은 서버 기능이 물리 장비, 가상 머신, 외부 서비스에 흩어져 있을 수 있다. 소유자와 적용 범위를 먼저 확인하고, 어느 팀이 설정·점검·복구를 맡는지 분명히 한다.
- **시스템 보안 진단:** 승인된 범위에서 서버와 설정 상태를 평가하고 조치 우선순위와 재확인 결과를 보고한다. 운영자가 직접 변경을 적용하는 업무와 평가자의 판단은 구분한다.

대표 결과물은 시스템·소유자 목록, 보호 기준과 예외 기록, 변경 승인·적용 기록, 진단 보고서와 조치 확인이다. 목록 자체보다 **그 목록이 실제 운영 환경과 맞는지** 설명할 수 있어야 한다.

## 연결되는 직무와 협업

[시스템·인프라 보안 엔지니어](/careers/infrastructure-security-engineer/)는 보호 기준을 운영에 적용하고, [인프라 보안 진단 담당자](/careers/infrastructure-security-assessor/)는 승인된 환경의 상태와 개선 결과를 평가한다. [보안 아키텍트](/careers/security-architect/)는 시스템 설계·변경의 기준을 정하는 데 관여할 수 있다. [보안 솔루션 구축·운영 엔지니어](/careers/security-solution-engineer/)는 해당 환경에 들어간 보호 도구를 안정적으로 운영하고, [취약점 관리 담당자](/careers/vulnerability-management-specialist/)는 발견된 문제의 조치와 재확인 흐름을 관리한다. 이 직무들이 모두 한 팀이나 한 공고에 등장하는 것은 아니다.

## 다른 분야와의 경계

[네트워크 보안](/fields/network/)은 시스템 **사이의 연결과 통신 정책**에 초점을 둔다. [클라우드·컨테이너 보안](/fields/cloud/)은 서비스 제공자가 운영하는 자원과 개발팀이 함께 쓰는 플랫폼에서 책임을 나누는 일이 더 두드러진다. 서버가 클라우드에 있거나 네트워크 정책이 얽혀 있다면 여러 분야의 담당자가 함께 결정한다. 단순한 일반 IT 운영 공고를 모두 시스템 보안 전담 채용으로 읽지 않는다.

## 진입과 공고 읽기

시스템 운영 경험이 있다면 변경 요청을 받았을 때 보호 대상·소유자·승인자·결과를 정리한 사례가 출발점이 된다. 경험이 없으면 가상의 서버 도입을 두고 어떤 팀에 무엇을 확인할지, 어떤 기록을 남길지 한 장의 업무 메모로 구성해 볼 수 있다. 실제 고객의 서버 이름이나 구성도는 공개 포트폴리오에 넣지 않는다.

공고에서는 운영과 진단 중 무엇이 중심인지, 담당 환경이 사내 시스템인지 고객사 환경인지, 장애·당직·교대가 있는지, 변경 승인 권한이 누구에게 있는지 확인한다. 특정 도구 이름이나 자격증이 적혀 있어도 필수와 우대를 나누어 읽는다. 분야 이름은 채용 직함과 같지 않으므로 지원 조건은 해당 공고 원문에서 다시 확인한다.
