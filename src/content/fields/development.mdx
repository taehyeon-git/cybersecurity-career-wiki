## 한눈에 보기

서비스·제품을 **만들거나 바꿀 때** 보안 문제가 반복되지 않도록 개발 과정에 참여한다. 출시 직전 검사만 하는 일이 아니다. 무엇을 확인해야 하는지 정하고 개발팀이 수정할 수 있는 의견을 남기며, 수정이 실제로 반영됐는지 확인한다. 이 분야의 모두가 같은 양의 코드를 작성하지는 않는다.

## 실제 하루와 판단

새 기능의 대상 사용자, 다룰 정보, 예상 밖의 사용과 장애 영향을 제품팀과 확인한다. 설계 검토 의견을 남기고 개발·테스트·출시 과정에서 누가 어떤 문제를 고칠지 조율한다. 수정 뒤에는 원래 문제가 해결됐는지와 다른 사용 흐름의 영향도 확인한다. 핵심 판단은 **어떤 위험을 출시 전에 줄여야 하며, 예외는 누가 받아들이는가**다.

## 세부 분야

- **전체 서비스 설계:** 보안 아키텍트는 서비스와 팀을 가로지르는 보호 원칙을 정리하고 중요한 예외의 승인 경로를 만든다. 개발팀이 특정 기능을 바꿀 때 참고할 설계 기준과 검토 의견이 남는다.
- **애플리케이션 보안(AppSec)과 개발 과정:** 앱 보안 담당자는 반복되는 개발 문제를 찾아 수정 가능한 요구로 바꾸고, 개발·배포 과정 담당자는 점검과 예외 처리가 계속 돌아가도록 돕는다. 두 역할 모두 발견 건수보다 실제 수정과 재발 여부를 확인해야 한다.
- **모바일·기기·제품 보안:** 앱, 펌웨어, 연결된 기기는 변경·업데이트·고객 사용 조건이 서로 다르다. 담당자는 해당 제품의 출시와 유지보수 팀에 보안 요구, 영향 범위, 확인 결과를 전달한다. 이 업무는 보안 솔루션 자체의 기능을 만드는 [보안제품 기획·개발·품질](/fields/product/)과 목적이 다를 수 있다.
- **개인정보·암호·AI 기능:** 정보 처리 방식이나 특정 기능의 보호 요구를 제품 설계에 연결한다. 개인정보 담당 조직, 연구자, 개발자가 같은 결론을 볼 수 있도록 요구사항과 선택의 한계를 기록한다. 어느 한 전문 분야의 학위·경력이 모든 설계 직무에 필요한 것은 아니다.
- **공개 프로젝트 보안:** 오픈소스 프로젝트로 들어온 제보의 처리, 수정·배포, 기여자와의 조율을 맡을 수 있다. 공개 프로젝트를 유지하는 책임과 회사가 사용하는 외부 구성요소를 관리하는 책임은 공고에서 구분한다.

이 구분은 관심 대상을 찾기 위한 것으로, 한 팀이 여러 부분을 맡을 수 있다.

## 함께 일하는 직무와 결과물

- [보안 아키텍트](/careers/security-architect/), [애플리케이션 보안 엔지니어](/careers/application-security-engineer/), [데브섹옵스 엔지니어](/careers/devsecops-engineer/): 넓은 설계 기준, 개발팀의 반복 문제, 개발·배포 과정의 적용.
- [제품 보안 엔지니어](/careers/product-security-engineer/), [모바일 보안 엔지니어](/careers/mobile-security-engineer/), [펌웨어 보안 엔지니어](/careers/firmware-security-engineer/): 제품·앱·기기 환경의 요구와 검증.
- [개인정보보호 엔지니어](/careers/privacy-engineer/), [암호기술 엔지니어](/careers/cryptography-engineer/), [AI 보안 엔지니어](/careers/ai-security-engineer/): 정보 처리나 특정 기능의 요구와 검증.
- [오픈소스 보안 엔지니어](/careers/open-source-security-engineer/): 공개 프로젝트의 제보·수정·배포·기여자 조율.

보안 요구사항, 설계 검토 의견, 개발팀 점검 기준, 변경·예외 기록, 출시 판단을 위한 검증 결과가 남는다. 제품 관리자·개발자·품질 검증(QA)·개인정보·운영팀과 일한다.

## 입문과 전환

개발·QA·제품 운영 경험이 있다면 도구 이름보다 **어떤 변경을 제안했고, 누가 동의했으며, 무엇으로 결과를 확인했는가**를 보여준다. 가상의 서비스 변경에 대한 한 페이지 검토 의견서는 연습 자료가 될 수 있다. 경험을 실제 프로젝트와 가상 과제로 분리해 표시한다.

## 공고 읽기와 남은 한계

직함보다 설계 자문, 직접 구현, 자동화 운영, 출시 승인 중 주 책임을 찾는다. AI나 암호 분야의 특정 공고가 요구한 학위와 연수를 모든 설계·개발 직무의 조건으로 옮기지 않는다. 독립 직접 공고가 부족한 세부 역할도 있으므로 해당 직무 글의 근거 범위를 함께 본다.
