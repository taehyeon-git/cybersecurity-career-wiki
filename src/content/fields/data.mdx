## 한눈에 보기

데이터 보안은 회사가 가진 정보가 **어디에 있고, 누가 어떤 목적으로 쓸 수 있으며, 밖으로 이동하거나 오래 남을 때 어떤 위험이 생기는지**를 살피는 분야다. 고객 기록, 업무 문서, 분석 자료, 기계가 만든 기록처럼 보호할 대상은 다양하다. 모든 데이터를 똑같이 잠그는 것이 목표는 아니다. 필요한 사람이 맡은 일을 하면서도 불필요한 접근과 노출을 줄이는 기준을 세우고, 적용 결과를 확인한다.

데이터 보안과 개인정보 보호는 가까우나 책임이 같지는 않다. 데이터 보안은 데이터의 접근·이동·보관을 보호하는 기술·운영 통제에 초점을 둘 수 있다. 개인정보 보호는 왜 수집하고 어떻게 이용·보관·파기하며 이용자 권리를 어떻게 보장하는지와 같은 법·처리 책임까지 다룬다. 회사에서는 두 팀이 같은 자료를 놓고 함께 판단할 수 있다.

## 현장에서 하는 일

새 분석 서비스가 고객 데이터를 사용하려 한다고 가정해 보자. 데이터 보안 담당자는 원본과 가공된 자료가 어디에 저장되는지, 개발·운영·외부 업체 중 누가 접근하는지, 분석 뒤 결과가 어디로 이동하는지 확인한다. 필요한 접근을 전부 막지 않고 목적과 기간에 맞게 범위를 조정한다. 정해진 기준이 실제 시스템에 적용됐는지 운영팀과 확인하고, 예외가 생기면 소유자와 종료 시점을 기록한다. 개인정보 담당자는 처리 목적과 권리 안내 등 별도 판단이 필요한 부분을 검토한다.

산출물은 중요 데이터 목록과 책임자, 접근·사용 기준, 예외와 승인 기록, 유출방지·암호화 등 보호 조치의 적용 상태, 변경 후 재확인 결과가 될 수 있다. '보호 솔루션을 설치했다'는 말만으로 정보가 실제로 보호됐다고 결론 내리지 않는다. 데이터가 복사되거나 분석 환경으로 옮겨질 때도 같은 보호 약속이 이어지는지 봐야 한다.

## 세부 갈래

- **저장·분석 환경:** 데이터베이스, 파일 저장소, 분석용 자료를 다룬다. 어느 사본이 업무에 필요한지, 소유자와 보관 기간이 누구의 책임인지 정리한다.
- **금융·결제 정보:** 거래 기록과 고객 정보를 다루는 서비스에서는 해당 정보의 보관·공유·접근 범위를 서비스 소유자와 확인한다. 결제 기능 자체의 설계는 [웹·애플리케이션 보안](/fields/web/), 암호 기능과 키의 운영은 [암호·키 관리 보안](/fields/cryptography/) 담당자와 나누어 본다.
- **접근과 사용:** 직원·서비스·외부 업체가 필요한 범위에서만 자료를 쓰도록 기준을 세우고 과도한 권한과 방치된 예외를 줄인다. 권한 체계 자체의 전문 설계는 [신원·접근 보안](/fields/identity/)과 맞닿는다.
- **이동과 유출 방지:** 자료를 내려받거나 다른 환경으로 보낼 때 예상치 못한 노출이 있는지 살핀다. [NIST의 데이터 유출 방지 용어 설명](https://csrc.nist.gov/glossary/term/data_loss_prevention)은 이 주제의 한 부분을 정의하지만, 도구 하나가 모든 데이터 위험을 해결한다는 뜻은 아니다.
- **암호와 키 운영:** 보호가 필요한 정보를 적절히 암호화하고, 이를 가능하게 하는 키의 소유·변경·복구 책임을 함께 확인한다. 상세 역할은 [암호·키 관리 보안](/fields/cryptography/)에 이어진다.
- **개인정보 처리와 영향평가:** 개인정보가 포함되면 처리 목적, 이용자 권리, 법정 평가 대상인지 같은 질문이 추가된다. 이는 데이터 보안 엔지니어의 기술 통제와 협업하지만 동일한 직무 자격이나 승인권을 뜻하지 않는다.

## 직무와 책임 경계

[데이터 보안 엔지니어](/careers/data-security-engineer/)는 저장·분석·업무 환경에 걸쳐 접근과 보호 통제를 설계·운영하는 직접 직무다. [개인정보보호 엔지니어](/careers/privacy-engineer/)는 제품의 정보 처리 요구를 설계와 데이터 흐름에 반영하는 인접 기술 역할이다. [개인정보보호 담당자](/careers/privacy-manager/)는 처리 목적과 이용자 권리 등 운영 책임을, [개인정보 보호책임자(CPO)](/careers/chief-privacy-officer/)는 조직 차원의 법정 책임을 맡는 별도 리더십 직무다. [개인정보 영향평가 수행자](/careers/privacy-impact-assessment-specialist/)는 정해진 대상과 절차에 따라 처리 흐름과 위험을 평가한다. 이 역할들을 모두 '데이터 보안 엔지니어'로 읽지 않는다.

제품팀은 데이터 사용 목적을, 플랫폼팀은 저장·변경 조건을, 개인정보·법무팀은 처리 책임을, 사업 책임자는 필요한 업무와 수용 가능한 위험을 설명한다. 발견 사항을 누구에게 올리고 누가 최종 승인하는지는 조직마다 다르다.

## 입문과 채용 공고

데이터 엔지니어링, 시스템·클라우드 운영, 접근관리, 개인정보 운영 경험에서 전환할 수 있다. 공개 가능한 가상 서비스의 데이터 종류와 흐름을 그리고, 담당자·접근 목적·보관 위치·예외 승인·재검토 날짜를 정리해 보자. 실제 고객 자료나 회사의 접근 기록은 포트폴리오에 넣지 않는다. 무엇을 막았는가뿐 아니라 필요한 업무를 유지하면서 어떻게 범위를 줄였는지를 설명하면 좋다.

공고에서는 보호 대상이 고객 개인정보인지 일반 기업 정보인지, 설계·구축·운영 중 어느 단계가 주업무인지, 개인정보 법·정책 판단까지 맡는지 확인한다. 특정 제품·클라우드·암호 기술 경험은 필수와 우대를 구분한다. [NIST 사이버보안 프레임워크](https://www.nist.gov/cyberframework)는 조직의 위험 관리에 쓰이는 넓은 틀이고, [개인정보보호위원회의 영향평가 안내](https://pipc.go.kr/np/default/page.do?mCode=D050020000)와 [개인정보 보호법의 보호책임자 조항](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1033214941)는 개인정보 역할의 별도 책임을 이해하는 자료다. 이 자료의 존재가 모든 데이터 보안 공고에 같은 자격을 요구한다는 뜻은 아니다.

데이터가 놓인 인프라는 [시스템 보안](/fields/system/)과 [클라우드 보안](/fields/cloud/)에서, 단말에 남는 사본은 [엔드포인트 보안](/fields/endpoint/)에서 더 자세히 살펴볼 수 있다. 여러 분야가 같은 데이터를 보더라도 각 담당자의 결정권과 산출물은 다르다.
