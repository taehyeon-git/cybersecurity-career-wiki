## 한눈에 보기

웹·애플리케이션 보안은 브라우저로 이용하는 서비스와 그 뒤의 애플리케이션 기능·사용자 권한·정보 처리 흐름을 안전하게 만들고 유지하는 일이다. 예를 들어 예약 서비스의 고객은 자기 예약만 보고 바꿀 수 있어야 한다. 보안 담당자는 이 원칙이 화면뿐 아니라 서비스가 요청을 처리하는 곳에도 적용되는지 개발팀과 확인한다. 출시 직전 한 번의 점검으로 끝나지 않는다. 기능과 이용자가 계속 바뀌므로 설계, 개발, 출시, 운영 중 제보와 수정이 이어진다.

이 분야를 **웹사이트를 공격하는 일**로만 생각하면 직무 선택이 어려워진다. 한 팀은 설계 조언과 개발자 교육을, 다른 팀은 허가받은 진단과 재확인을, 또 다른 팀은 여러 제품의 공통 기준을 맡는다. 어느 역할이든 문제의 이름보다 영향받는 사용자와 기능, 수정 책임자, 남은 위험을 설명하는 능력이 중요하다.

## 실제 업무와 판단

새로운 결제·예약 기능이 생긴다고 가정해 보자. 보안 담당자는 어떤 사용자가 어떤 정보에 접근하는지, 외부 업체와 주고받는 정보가 무엇인지, 기능이 실패했을 때 누가 알아차리는지 제품·개발팀에 묻는다. 금융·결제 서비스에서는 거래 기능의 허용 범위와 이용자 안내까지 제품팀과 확인하되, 거래 기록의 보관·공유는 데이터 보안 담당자와, 암호 기능과 키는 암호·키 관리 담당자와 역할을 나눈다. 설계 검토에서 우려가 나오면 개발자가 바꿀 수 있는 요구사항으로 정리한다. 출시 전 확인 결과는 재현 조건과 영향을 함께 전달하고, 수정 뒤에는 같은 문제가 해결됐는지 검증한다. 일정상 남는 문제는 누가 승인하고 언제 다시 볼지 기록한다.

대표 산출물은 기능별 보안 요구, 검토 의견, 범위가 적힌 진단 보고서, 수정·재확인 기록, 출시 결정에 필요한 잔여 위험 설명이다. 기술적 발견만 길게 적고 고객이나 개발팀이 무엇을 해야 하는지 빠뜨리면 좋은 결과물이 아니다.

## 세부 갈래

- **서비스 설계와 개발 협업:** 기능을 만들기 전에 보호할 정보와 사용자 권한을 정하고, 반복되는 결함이 설계나 개발 절차에서 생기는지 살핀다. 개발자가 계속 사용할 기준과 변경 검토 기록이 남는다.
- **웹 기능과 API:** 화면 뒤에서 다른 프로그램이 기능을 호출하는 통로를 API라고 한다. 같은 서비스라도 화면과 API의 사용자·권한·정보 노출 경계가 다를 수 있다. 담당자는 어느 기능과 이용자에게 영향이 있는지 구분해 결과를 전달한다.
- **허가된 웹 진단:** 정해진 서비스·계정·시간 안에서 취약 가능성을 확인하고, 개발팀이 재현·수정할 수 있는 근거를 남긴다. 이 일은 서비스를 계속 설계하는 역할과 협업하지만 같은 업무량이나 권한을 뜻하지 않는다.
- **개발·배포 과정의 보안:** 여러 개발팀이 변경할 때 점검 결과가 담당자에게 가고 예외가 기록되는 흐름을 만든다. 도구를 설치한 사실보다 발견 사항이 실제 수정과 재발 방지로 이어졌는지가 결과다.

## 관련 직무와 협업

[애플리케이션 보안 엔지니어](/careers/application-security-engineer/)는 제품팀과 지속해서 설계·코드·변경을 검토한다. [웹 모의침투 테스터](/careers/web-penetration-tester/)는 허가받은 범위에서 특정 서비스의 위험을 검증하고 보고한다. [데브섹옵스 엔지니어](/careers/devsecops-engineer/)는 개발·배포 과정의 점검과 수정 흐름을 운영한다. [제품 보안 엔지니어](/careers/product-security-engineer/)는 웹 기능을 포함한 제품 전체의 출시·운영 위험을 맡을 수 있다. 이 넷이 한 회사에서 모두 별도 채용되는 것은 아니며, 공고가 여러 책임을 묶을 수 있다.

제품 관리자와 개발자는 기능·일정을, 개인정보 담당자는 처리 목적과 이용자 권리를, 운영팀은 실제 배포·장애 조건을 설명한다. 보안 담당자가 최종 출시 결정을 혼자 내리는지, 의견을 주고 승인자에게 올리는지는 조직별로 다르다.

## 입문과 공고 읽기

웹 개발·품질 검증 경험이 있다면 자신이 맡은 기능 하나를 골라 사용자, 보호할 정보, 변경 요청, 발견 사항, 수정 확인을 한 장에 정리해 보자. 공개 가능한 가상 서비스나 본인이 만든 프로젝트를 사용하고, 실제 고객 서비스는 승인 없이 시험하지 않는다. 처음부터 모든 웹 기술을 외우는 것보다 문제를 개발자에게 명확히 전달하고 수정 후 결과를 확인한 사례가 더 적합한 포트폴리오가 될 수 있다.

공고에서는 **담당 서비스가 웹·API·모바일 중 어디까지인지**, 설계 자문과 진단 중 무엇이 주업무인지, 직접 수정 권한과 출시 승인권이 있는지 확인한다. 특정 언어·도구·자격증과 경력 연수는 해당 공고의 필수·우대 칸을 나눠 읽는다. [NIST의 안전한 소프트웨어 개발 프레임워크](https://csrc.nist.gov/pubs/sp/800/218/final)는 개발 전반의 실천을 설명하고, [OWASP 웹 목록](https://top10.owasp.org/2025/)과 [API 목록](https://api-security.owasp.org/editions/2023/en/0x11-t10/)은 위험 주제를 정리한다. 이 자료들이 채용 직함이나 모든 회사의 필수 요건을 정하지는 않는다.

웹 서비스가 놓인 서버의 설정은 [시스템 보안](/fields/system/)이나 [클라우드 보안](/fields/cloud/)에, 휴대전화 앱 자체의 배포와 기기 조건은 [모바일 앱 보안](/fields/mobile/)에 더 가깝다. 사용자 정보의 처리·권리 문제는 [데이터 보안](/fields/data/)과 함께 읽는다. 금융·결제 서비스의 암호 기능과 키 운영은 [암호·키 관리 보안](/fields/cryptography/)도 참고한다.

제품팀과 지속해서 설계·출시 판단에 참여하는 일을 준비한다면 [애플리케이션 보안 커리어 경로](/roadmaps/application-security/)를, 허가된 범위에서 서비스를 평가하고 결과를 보고하는 일을 준비한다면 [보안 평가·침투 테스트 커리어 경로](/roadmaps/penetration-testing/)를 읽어 지원 자료의 초점을 정할 수 있다.
