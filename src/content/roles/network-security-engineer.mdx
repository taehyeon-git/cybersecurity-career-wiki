## 왜 필요한가

서비스 간 통신을 무조건 열거나 닫으면 각각 노출과 장애가 발생한다. 네트워크 보안 엔지니어는 실제 업무 흐름에 필요한 경로만 허용하고 변경이 예상대로 작동하는지 검증한다. NIST Zero Trust Architecture는 네트워크 위치만으로 신뢰를 부여하지 않는 방향을 제시한다.

## 운영 업무의 반복 주기

서비스가 새 경로로 통신해야 할 때 요청자의 목적, 연결의 양끝, 사용 기간, 장애 시 영향과 승인자를 확인한다. 기존 방화벽 규칙은 만든 당시의 사업 목적이 사라져도 남기 쉽다. 네트워크 보안 엔지니어는 변경 이력과 실제 사용을 점검해 불필요한 경로를 정리한다. 장애가 나면 보안 장비의 정책만 원인으로 단정하지 않고 네트워크 운영팀과 함께 경로·변경·성능 자료를 확인한다. 점검 결과를 서비스 담당자에게 이해 가능한 언어로 설명하는 것도 업무다.

## 정책과 변경 기록의 품질

접근 정책 표에는 출발지와 목적지, 허용 서비스, 업무 근거, 책임자, 만료 또는 정기 재검토일, 검증 결과를 남긴다. 예외 규칙은 누가 승인했고 어떤 임시 보완책이 있는지 기록한다. 장애 대응 기록에는 증상이 처음 나타난 시각, 영향받은 서비스, 되돌린 변경, 남은 위험을 적는다. 정책 수가 많거나 차단 건수가 높다는 사실만으로 안전한 운영을 증명할 수는 없다. 경로가 필요한 이유와 사용 종료 시점을 설명할 수 있어야 한다.

[티맵모빌리티의 2025년 종료된 Network & Endpoint Security Architect 공고](https://www.skcareers.com/Recruit/Detail/R250912)는 오피스망·내부 네트워크 설계, 직원·협력업체 단말 기준, SaaS 도입 검토를 **한 복합 직함**에 묶었다. 경력 정규직이지만 숫자로 된 필수 연차는 원문에 표시되지 않았다. 네트워크 보안 책임을 제목에 직접 드러내는 사례이나, 단말 보안 아키텍트의 채용 한 건을 별도의 네트워크·단말 채용 두 건으로 세지 않는다.

## 진입 경로와 면접 근거

네트워크 운영 경험에서는 장애 복구와 변경 절차를, 공급사 기술지원 경험에서는 고객 문제 해결을 연결할 수 있다. 사내 보안 역할로 이동할 때는 규칙의 소유자, 위험 수용, 예외 만료를 끝까지 추적한 범위를 구분해 설명한다. 면접에서는 오래된 정책을 정리하거나 서비스 중단 없이 변경한 결정 과정을 보여주고, 특정 벤더 명령어를 모든 조직의 필수 역량으로 일반화하지 않는다.

## 지원용 포트폴리오

### 사례 1: 업무 흐름을 반영한 접근 변경 요청

가상의 신규 서비스가 기존 사용자 구역과 자료 저장소 사이에 연결을 요청한다. 요청 목적, 필요한 통신의 소유자, 허용 기간, 영향을 받는 기존 업무, 승인자를 한 장에 정리한다. 모든 연결을 차단하거나 허용하는 답 대신 **서비스가 작동하는 데 필요한 범위를 누가 확인했는지** 보여준다. 실제 회사의 망 구성과 주소는 공개하지 않는다.

### 사례 2: 변경 실패의 운영 인계서

변경 뒤 일부 정상 업무가 중단됐다는 합성 상황을 만든다. 영향 확인자, 되돌릴 조건, 고객 안내 주체, 재검토할 변경 요청을 적는다. 산출물은 규칙 명령의 나열이 아니라 다른 교대자가 상황을 이어받을 수 있는 결정 기록이다. 면접에서는 빠른 복구와 남은 위험의 확인을 어떻게 함께 관리할지 설명한다.

## 지원 전에 확인할 질문

- 회사 내부의 정책 운영인가, 보안 제품 고객사의 기술지원인가?
- 방화벽·네트워크 변경의 승인권과 장애 때의 롤백 책임은 어느 조직에 있는가?
- 새 서비스의 연결 설계와 오래된 규칙 정리 중 어느 일이 더 많은가?
- 클라우드·사내망·원격 근무 연결의 범위가 어디까지인지 확인한다.

같은 '네트워크 보안 엔지니어' 제목이라도 고객 응대 능력과 사내 정책 소유권은 다르게 평가된다. 지원자는 변경 요청의 업무 근거를 확인한 경험, 장애 대응 시각과 통제 예외의 재검토를 기록한 사례를 각각 준비하면 맡을 책임을 설명하기 쉽다.

## 근거와 확인 범위

공식 역할 자료는 네트워크 운영·보안 통제의 일반 업무를 보여준다. 국내 공고는 상세 확인 정도가 다르므로 제목만 확인된 사례에서 필수 기술을 추론하지 않는다.
