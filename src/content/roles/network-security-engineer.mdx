## 왜 필요한가

서비스 간 통신을 무조건 열거나 닫으면 각각 노출과 장애가 발생한다. 네트워크 보안 엔지니어는 실제 업무 흐름에 필요한 경로만 허용하고 변경이 예상대로 작동하는지 검증한다. NIST Zero Trust Architecture는 네트워크 위치만으로 신뢰를 부여하지 않는 방향을 제시한다.

## 실제 수행 업무

- **입력:** 서비스 통신 요구, IP·DNS·포트 정보, 기존 정책, 변경 창과 장애 영향.
- **과정:** 데이터 흐름과 신뢰 경계를 그린다. 최소 범위의 정책을 설계하고 시험 환경에서 허용·차단 사례를 확인한 뒤 운영 로그를 관찰한다.
- **출력:** 변경 이유, 대상·기간·소유자, 롤백 절차, 실제 테스트 결과가 있는 정책 기록.

## 가상 실무 시나리오

**가상 시나리오:** 개발팀이 새 API와 데이터베이스 연결을 요청한다. 엔지니어는 API 워크로드만 데이터베이스 포트에 접근하도록 경로를 좁히고, 일반 사용자망에서는 접근이 거부되는지 시험한다. 배포 후 차단 로그에서 정상 트래픽 누락이 있는지 확인한다. 예외 규칙은 담당자와 만료일을 붙인다.

## 업무에서 쓰는 역량과 도구

패킷 캡처는 실제 통신을 확인하고, 정책 관리 도구는 규칙의 변경 이력을 남기며, 다이어그램은 업무 흐름과 차단 지점을 공유한다. 차단 로그의 부재가 안전의 증거는 아니다. [NIST SP 800-207](https://csrc.nist.gov/pubs/sp/800/207/final)의 자원 중심 접근 원칙을 참조한다.

## 신입 준비

‘네트워크 보안’, ‘방화벽 운영’, ‘클라우드 네트워크 보안’ 공고는 장비 운영과 설계 비율이 다르다. 작은 가상망에서 통신 행렬과 허용·차단 테스트를 설명할 수 있어야 한다. 특정 벤더 명령어 경험은 환경에 따라 유용하지만 보편적인 필수 요건은 아니다.

## 포트폴리오 작업 예시

### 프로젝트 1: 세 구역 가상망 분리

- **목표·선수 지식·환경:** 사용자·API·DB 구역을 분리한다. IP·라우팅 기초와 로컬 가상망이 필요하다.
- **작업·검증:** 통신 행렬을 작성하고 정책 적용 전후에 각 경로를 시험한다.
- **산출물·완료 기준·포트폴리오:** 흐름도, 규칙, 허용·차단 증거를 제출한다. DB 직접 접근은 막고 API 경로는 유지되면 완료다.

### 프로젝트 2: 정책 변경과 롤백

- **목표·선수 지식·환경:** 잘못된 규칙으로 인한 장애를 안전하게 되돌린다. 방화벽 기초와 첫 프로젝트 환경이 필요하다.
- **작업·검증:** 의도적 차단 오류를 넣고 모니터링·롤백 절차를 실행한다.
- **산출물·완료 기준·포트폴리오:** 변경 요청, 시험 결과, 롤백 시간표를 남긴다. 정상 통신 복구가 확인되면 완료다.

## 운영 업무의 반복 주기

서비스가 새 경로로 통신해야 할 때 요청자의 목적, 연결의 양끝, 사용 기간, 장애 시 영향과 승인자를 확인한다. 기존 방화벽 규칙은 만든 당시의 사업 목적이 사라져도 남기 쉽다. 네트워크 보안 엔지니어는 변경 이력과 실제 사용을 점검해 불필요한 경로를 정리한다. 장애가 나면 보안 장비의 정책만 원인으로 단정하지 않고 네트워크 운영팀과 함께 경로·변경·성능 자료를 확인한다. 점검 결과를 서비스 담당자에게 이해 가능한 언어로 설명하는 것도 업무다.

## 정책과 변경 기록의 품질

접근 정책 표에는 출발지와 목적지, 허용 서비스, 업무 근거, 책임자, 만료 또는 정기 재검토일, 검증 결과를 남긴다. 예외 규칙은 누가 승인했고 어떤 임시 보완책이 있는지 기록한다. 장애 대응 기록에는 증상이 처음 나타난 시각, 영향받은 서비스, 되돌린 변경, 남은 위험을 적는다. 정책 수가 많거나 차단 건수가 높다는 사실만으로 안전한 운영을 증명할 수는 없다. 경로가 필요한 이유와 사용 종료 시점을 설명할 수 있어야 한다.

## 준비할 경력 증거

가상 서비스 두 개의 통신 요청을 받아 승인 표와 변경 전후의 접근 결과를 작성하는 포트폴리오가 좋다. 장애를 가정해 롤백 조건과 담당자 연락 흐름을 함께 적는다. 면접에서는 규칙을 추가한 경험보다 오래된 규칙의 소유자를 찾아 정리하거나 서비스 중단 없이 정책을 전환한 과정을 설명한다. 네트워크 운영 경험에서 옮겨올 수 있으나 보안팀에서는 위험 수용과 예외 만료를 끝까지 추적하는 책임이 늘어난다. 공급사 기술지원 경험은 고객 문제 해결에 강점이지만 사내 정책 소유권과 동일하게 표현하지 않는다.

## 지원 전에 확인할 질문

- 회사 내부의 정책 운영인가, 보안 제품 고객사의 기술지원인가?
- 방화벽·네트워크 변경의 승인권과 장애 때의 롤백 책임은 어느 조직에 있는가?
- 새 서비스의 연결 설계와 오래된 규칙 정리 중 어느 일이 더 많은가?
- 클라우드·사내망·원격 근무 연결의 범위가 어디까지인지 확인한다.

같은 '네트워크 보안 엔지니어' 제목이라도 고객 응대 능력과 사내 정책 소유권은 다르게 평가된다. 지원자는 변경 요청의 업무 근거를 확인한 경험, 장애 대응 시각과 통제 예외의 재검토를 기록한 사례를 각각 준비하면 맡을 책임을 설명하기 쉽다.

## 근거와 확인 범위

공식 역할 자료는 네트워크 운영·보안 통제의 일반 업무를 보여준다. 국내 공고는 상세 확인 정도가 다르므로 제목만 확인된 사례에서 필수 기술을 추론하지 않는다.
