## 왜 필요한가

보안 통제가 실제 운영되어도 책임자·[위험 수용](/glossary/#riskacceptance) 결정·증거가 연결되지 않으면 조직은 무엇이 관리되고 있는지 설명하기 어렵다. GRC 분석가는 정책, 위험, 통제, 증거, 예외를 같은 흐름으로 관리한다. NIST CSF 2.0의 Govern 기능은 전략·역할·정책·감독 결과를 다룬다.

## 계속 돌아가는 관리 업무

GRC는 인증 심사 직전에만 문서를 모으는 일이 아니다. 정책 개정 요청과 신규 서비스의 위험 검토가 들어오면 적용 범위, 통제 책임자, 현재 증거가 맞는 시점을 확인한다. 통제 운영팀의 답변이 늦어지면 경영 보고 일정과 위험 수용 기한을 조정한다. 분기 말에는 만료된 예외와 미완료 개선조치를 다시 열고, 실제 조치가 되었는지 증거로 확인한다. 감사 대응과 일상 위험 관리를 같은 표에서 추적하되 독립 감사의 판단을 대신하지 않는다.

## 관리 문서의 예시

위험 등록부 한 행에는 위험 시나리오, 영향을 받는 서비스, 사업 영향, 기존 통제, 소유자, 잔여 위험, 승인권자, 다음 검토일이 필요하다. 통제 증거 목록에는 문서명만 쓰지 말고 생성 시점·대상 범위·검증 담당자를 기록한다. 예외 승인에는 종료 조건이 있어야 한다. 이를 지키면 정책 문구와 실제 운영 사이에 간격이 생겨도 누구에게 어떤 결정을 요청해야 하는지 분명해진다.

## 국내 채용에서 확인한 업무

2026-10-09 확인한 토스의 [Information Security Manager (보안정책)](https://toss.im/career/job-detail?job_id=7711619003)은 금융·개인정보 규제를 내부 정책과 통제로 해석하고 인증·점검 증적과 개선을 관리하는 업무를 적었다. LINE studio의 [Senior Security Professional (게임서비스 분야)](https://careers.linecorp.com/ko/jobs/3111/)은 2026-09-11 게시 공고에서 관리체계·개인정보·외부 SOC 조율을 한 직무에 결합했으며 7년 이상을 요구했다. 두 사례는 조직별 범위 차이를 보여주며 GRC 전체의 공통 경력 조건을 뜻하지 않는다.

2026-10-25 확인한 엘리스그룹의 [보안 GRC 매니저](https://www.elice.careers/jobs?recordId=recvFaZeA0zLROXJS)는 인증 통제 매핑과 증적 자동화, 보유 인증 유지·신규 인증 갭 분석, 위험평가·자산관리·내부감사·직원 교육을 **한 내부 관리 자리**에 묶었다. 공고는 정보보호·개인정보 실무 **5년 이상**과 인증 취득·사후관리, 정책 문서 작성 경험을 요구하며 보안 자격증은 우대한다. 실제 직함은 `매니저`여서 이 문서의 `분석가`와 동일한 조직상 직급이라고 볼 수 없다. 독립 인증 심사기관의 판정 업무도 아니다. 고용형태 칸은 비어 있고 게시·마감일이 없어 현재 충원 여부를 지원 버튼만으로 확정하지 않는다.

**인접 IT 회복력 업무:** 2026-10-25 확인한 토스뱅크의 [IT Governance Manager (BCP) 공고](https://toss.im/career/job-detail?job_id=7531919003)는 보안 GRC가 아닌 **IT 거버넌스팀**에서 [업무연속성계획(BCP)](/glossary/#businesscontinuityplan) 수립·운영과 그에 포함된 [IT 재해복구계획(DRP)](/glossary/#disasterrecoveryplan), ISO 22301 심사, 재해복구 모의훈련, 제3자 IT 위험·위탁 계약 관리를 맡긴다. BCP에 따른 비상대응훈련·비상대책위원회 운영 경험과 ISO 22301 요구사항 이해·인증심사 대응 경험은 필요 조건이고, 재해복구 모의훈련 주도와 주요 계약 검토 경험은 우대 조건이다. 정규직 공고지만 게시일과 필수 경력 연수는 표시되지 않았다. 이는 GRC와 접점이 있는 **IT 거버넌스 채용**이며 보안 GRC 분석가가 기술 복구를 실행한다는 근거는 아니다.

토스의 정책 중심 자리를 준비한다면 규제 요구 한 가지가 서비스 변경의 어떤 통제·운영 증거로 이어졌는지 보여준다. LINE studio처럼 관리체계·개인정보·외부 SOC 조율을 한 자리에 묶은 공고에는 외부 운영팀이 만든 자료와 자신이 검토·조정한 결정을 구분해 적는다. 어느 사례에서도 독립 감사 의견이나 사업 책임자의 위험 수용을 자신의 권한으로 쓰지 않는다.

## 진입 경로와 면접 근거

운영·개발·감사 지원 경험에서 전환한다면 자신이 본 통제 실패와 후속 조치의 결정권자를 구분해 설명한다. 면접에서는 불완전한 증거를 받았을 때 어떤 판단을 보류했고 어느 팀에 추가 자료를 요청했는지 묻는다. 인증 심사 준비와 상시 위험 관리의 비율, 자격증 요구, 국내 법규의 적용 여부는 공고와 제도를 각각 확인한다.

## 지원용 포트폴리오

### 사례 1: 사업 맥락이 있는 위험 등록부

가상의 서비스가 외부 업체에 일부 운영을 맡긴다는 상황을 정한다. 위험의 원인과 영향을 받는 업무, 이미 있는 통제, 미확인 정보, 결정권자를 한 표에 담는다. 평가 점수를 임의로 정답처럼 쓰지 않고 **왜 이 위험을 먼저 다뤄야 하는지** 담당자가 토론할 근거를 남긴다. 실제 외부 업체의 비공개 자료를 사용하지 않는다.

### 사례 2: 통제 증거의 빈틈 보고

정책에는 정기 검토가 명시돼 있지만 최근 운영 증거가 일부 기간에만 있는 상황을 만든다. 확인한 기간과 대상, 누락된 증거, 추가 자료 요청 담당자, 임시 판단을 구분해 짧은 보고서를 작성한다. 면접에서는 문서가 있다는 이유만으로 통제가 실제 운영됐다고 선언하지 않은 판단 과정을 설명할 수 있다.

## 지원 전에 확인할 질문

- 관리체계를 새로 구축하는가, 이미 운영 중인 통제의 증거와 개선을 맡는가?
- 위험 수용과 예외 승인권은 경영진·사업부·보안 조직 중 어디에 있는가?
- 특정 산업 인증 대응이 대부분인지 전사 위험 관리가 상시 업무인지 확인한다.
- 개인정보, 협력사 위험, 클라우드 검토까지 한 사람에게 묶여 있는가?
- BCP·IT 재해복구가 범위에 있다면 통제 증거와 제3자 위험 점검, 훈련·비상대책위원회 운영, 실제 시스템 복구 중 무엇을 맡고 누가 복구를 승인하는가?

'정책 담당'이라는 채용명에도 문서 작성만 기대하는 팀과 실제 사업 결정을 조정하는 팀이 있다. 면접에서는 법규 목록보다 소유자가 없는 통제를 어떻게 발견하고 누가 조치하도록 설득했는지를 사례로 보여준다.

작은 조직에서는 실무자가 정책 작성과 증거 수집을 함께 맡기도 한다. 이 경우에도 위험을 받아들이는 결정권자가 누구인지는 분명히 해야 하며, 한 사람이 모든 책임을 진다고 해석해서는 안 된다.

## 근거와 확인 범위

공식 프레임워크는 위험·정책·감독의 일반 책임을 뒷받침한다. 국내 공고는 확인 시점의 사례이며 하나의 채용명이 GRC의 모든 역할을 대표하지 않는다.
