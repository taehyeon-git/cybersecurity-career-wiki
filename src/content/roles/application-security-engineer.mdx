## 왜 필요한가

출시 직전 진단만으로는 설계 단계의 신뢰 경계 오류와 반복되는 코드 패턴을 충분히 줄이기 어렵다. 앱 보안 엔지니어는 개발팀과 함께 보안 요구사항을 코드와 테스트에 반영한다. NIST SSDF 1.1은 개발 수명주기에 통합할 수 있는 높은 수준의 안전한 개발 관행을 제공한다.

## 한 주의 업무는 어떻게 흘러가는가

새 기능의 설계가 올라오면 데이터 흐름과 권한 변경 범위를 먼저 확인하고 개발팀과 검토 시점을 잡는다. 배포 직전에는 발견된 문제의 재현 조건, 악용 가능한 사용자 범위, 수정 책임자를 기록한다. 모든 이슈를 동일한 긴급도로 처리하지 않는다. 사용 중인 기능인지, 외부 노출이 있는지, 보완 통제가 있는지를 제품 담당자와 확인한 뒤 출시 차단·기한 있는 수정·위험 수용 중 무엇을 제안할지 정한다. 수정 뒤에는 같은 조건에서 문제가 사라졌는지 다시 확인하고 회귀 가능성을 남긴다.

## 문서와 협업의 수준

좋은 검토 결과물은 취약점 이름만 적은 목록이 아니다. 예를 들어 권한 검토 기록에는 대상 기능과 두 사용자 역할, 기대한 접근 결과, 실제 관찰, 영향받는 데이터, 수정 담당자와 재검증일을 분리한다. 개발자는 어떤 동작을 바꿔야 하는지 알아야 하고 제품 책임자는 출시 판단에 필요한 잔여 위험을 알아야 한다. 보안 담당자는 재현 정보를 제한된 사람에게 공유하고 고객 데이터가 포트폴리오나 회의 자료로 새지 않게 관리한다.

## 국내 채용에서 확인한 업무 범위

2026-10-09 확인한 토스의 [Security Researcher (모의해킹/취약점 분석)](https://toss.im/career/job-detail?job_id=4076085003)은 웹·모바일·API·내부 시스템 진단과 출시 전 평가, 위협 모델링, 수정 권고를 한 포지션의 업무로 제시했다. 위키의 '애플리케이션 보안 엔지니어'와 업무가 겹치지만 공고의 실제 직함은 다르다. [Security Researcher (모바일보안)](https://toss.im/career/job-detail?job_id=7780944003)은 모바일 점검과 배포 과정의 보안 통합까지 요구했다. 두 공고의 환경과 요구 경력을 모든 AppSec 채용에 일반화하지 않는다.

두 공고는 지원서의 강조점도 다르게 만든다. 출시 전 평가가 중심인 자리에는 검토 의견이 어떤 수정·출시 판단으로 이어졌고 무엇을 다시 확인했는지 적는다. 모바일 보안 플랫폼을 만드는 자리에는 여러 개발자가 쓰는 검증 절차나 공통 기능에서 본인이 맡은 설계·적용·유지 범위를 적는다. 실제로는 의견만 제시했다면 플랫폼 구축을 본인의 성과로 쓰지 않는다. 면접에서는 검토 결과를 받는 개발팀과 최종 출시 결정자가 누구인지, 채택되지 않은 의견은 어떻게 기록하는지 물어 역할의 결정권을 확인한다.

## 입직과 전환을 위한 증거

신입 지원자는 개발팀의 변경 요청을 읽고 제품 담당자에게 확인할 질문을 제시할 수 있어야 한다. 개발 경험에서 전환한다면 직접 수정한 결함을 소재로 코드 검토 의견이 실제 출시 결정과 재검증으로 어떻게 이어졌는지 설명한다. 면접에서는 문제의 이름보다 우선순위를 정한 이유, 개발자 의견을 반영한 변경, 놓쳤던 가정을 구체적으로 말하는 편이 유용하다.

## 지원용 포트폴리오

### 사례 1: 출시 검토 의견서

가상의 서비스에 새 공유 기능이 들어온다는 요청을 설정한다. 사용자·제품 담당자에게 확인할 질문, 출시 전 반드시 확인할 권한 경계, 남은 미확인 사항을 한 장의 의견서로 정리한다. 포트폴리오에는 기능을 막거나 허용한 이유와 개발팀이 다시 확인할 기준을 함께 둔다. 평가자는 보안 용어의 수보다 **제품 결정을 돕는 근거와 책임자**가 분명한지 살필 수 있어야 한다.

### 사례 2: 반복 결함의 개선 제안

동일한 종류의 접근 문제 제보가 여러 기능에서 반복된다는 가상 상황을 만든다. 개별 결함 목록으로 끝내지 않고 공통 원인에 대한 가설, 개발팀이 받아들일 수 있는 리뷰 기준, 적용 범위를 제안한다. 산출물에는 반례와 예외 승인 주체도 적는다. 면접에서는 취약점 발견 건수보다 같은 문제가 다음 출시에서 줄어들도록 누구와 무엇을 바꿨는지 설명한다.

## 지원 전에 확인할 질문

- 신기능 설계 검토와 배포 직전 진단 중 어느 업무가 정기적인가?
- 개발자가 수정할 권한과 일정은 어느 팀이 결정하며 보안팀은 출시를 막을 수 있는가?
- 외부 제보나 고객 취약점 문의를 직접 처리하는가, 별도의 제품 보안 조직이 맡는가?
- 평가 대상이 웹·모바일·API 중 어디까지이며, 원격 조직과 협업하는 비율은 어느 정도인가?

공고에 'AppSec'라고만 적혀 있다면 위 질문으로 실제 책임을 좁혀야 한다. 면접에서 본인의 강점이 설계 리뷰인지 코드 분석인지, 개발팀과 수정 과정을 끝까지 추적한 경험인지 연결해 설명하면 직함보다 일의 적합성이 잘 드러난다.

## 근거와 확인 범위

역할의 일반적 책임은 이 문서의 공식 출처와 위 국내 공고의 확인된 업무를 함께 참고했다. 실제 채용에서는 보안 평가, 개발 지원, 제품 설계 중 어느 비중이 큰지 팀별로 다르며, 공고 종료나 수정 후에는 요구사항을 다시 확인해야 한다.
