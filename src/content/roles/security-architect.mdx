## 왜 필요한가

개별 팀의 통제가 각각 합리적이어도 연결 지점에 빈틈이 남을 수 있다. 보안 아키텍트는 데이터 흐름, 신원, 네트워크, 개발·운영 경계를 함께 검토해 목표 구조와 선택 이유를 남긴다. ENISA ECSF에는 Cybersecurity Architect 프로필이 있다.

## 실제 수행 업무

- **입력:** 사업·규제 요구, 현재 시스템 구조, 자산·데이터 분류, 위협 모델, 예산·운영 제약.
- **과정:** 보호 목표와 신뢰 경계를 정의하고 여러 통제 대안을 비교한다. 구현팀과 배포·장애·관측 가능성을 확인하고 예외 승인 기준을 정한다.
- **출력:** 참조 아키텍처, 설계 결정의 근거·가정, 구현 검증 항목, 잔여 위험과 소유자.

## 가상 실무 시나리오

**가상 시나리오:** 여러 팀의 API를 외부 파트너에게 제공한다. 아키텍트는 파트너 신원, API 인증, 서비스별 인가, 데이터 경계, 로그 요구를 묶어 설계한다. IAM·네트워크·AppSec 엔지니어와 각 통제의 책임 지점을 합의한다. 단일 게이트웨이만으로 서비스 내부 권한이 보장된다고 가정하지 않고 각 서비스의 검증 기준을 남긴다.

## 업무에서 쓰는 역량과 도구

아키텍처 다이어그램은 데이터·권한 흐름을 공유하고, 위협 모델 보드는 남은 질문을 추적하며, 결정 기록은 시간이 지나도 선택 이유를 보존한다. 도구보다 가정·대안·검증 방법의 명료성이 중요하다. [NIST SP 800-207](https://csrc.nist.gov/pubs/sp/800/207/final)은 자원 중심 접근의 참조 구조를 제공한다.

## 신입 준비

‘보안 아키텍트’는 대체로 여러 기술·조직을 연결하는 역할이므로 입문자는 네트워크·클라우드·AppSec 중 한 영역의 구현 경험을 쌓아 설계 근거를 축적할 수 있다. 특정 경력 연수나 자격증을 보편적 조건으로 단정하지 않는다. 포트폴리오는 다이어그램만이 아니라 선택·기각 대안과 검증 결과를 포함해야 한다.

## 포트폴리오 작업 예시

### 프로젝트 1: 다중 서비스 접근 설계

- **목표·선수 지식·환경:** 사용자·서비스 신원과 데이터 경계를 설계한다. IAM·네트워크 기초와 가상 시스템 요구사항이 필요하다.
- **작업·검증:** 현재·목표 구조를 그리고 권한 거부·서비스 장애 시나리오를 검토한다.
- **산출물·완료 기준·포트폴리오:** 결정 기록과 검증 항목을 낸다. 다른 사람이 통제 책임을 구분할 수 있으면 완료다.

### 프로젝트 2: 설계 예외 심사

- **목표·선수 지식·환경:** 통제 적용이 어려운 레거시 서비스의 대안을 평가한다. 위협 모델 기초가 필요하다.
- **작업·검증:** 즉시 수정·보완 통제·기한 있는 예외를 비교하고 모의 테스트로 각각의 한계를 확인한다.
- **산출물·완료 기준·포트폴리오:** 선택 이유, 잔여 위험, 재검토 조건을 제출한다. 승인자가 위험을 이해하고 결정할 수 있으면 완료다.

## 설계 검토의 시작점

보안 아키텍트는 모든 제품을 직접 설정하는 사람이라기보다 사업 요구를 보호 목표와 책임 구조로 바꾸는 사람이다. 신규 서비스나 큰 시스템 변경이 제안되면 데이터의 주인, 외부 연결, 운영팀의 권한, 장애 허용 범위와 규제 요구를 함께 묻는다. 설계안의 위험을 나열한 뒤 실행 가능한 선택지와 각 선택지의 비용·운영 부담을 정리한다. 합의한 원칙이 실제 구현에 반영되는지 변경 심의와 출시 검토에서 확인하고, 예외가 반복되면 아키텍처 원칙 자체를 재검토한다.

## 산출물은 의사결정을 남긴다

아키텍처 기록에는 현재 구조와 목표 구조, 보호할 자산, 신뢰 경계, 각 통제의 소유자, 실패 시 대응 경로, 남겨둔 위험과 승인자를 적는다. 다이어그램만 있으면 시간이 지나 왜 그 설계를 택했는지 알 수 없다. 대안별 장단점과 검증 결과를 기록해야 운영팀이 변경할 때도 근거를 추적할 수 있다. 개발·인프라·IAM·GRC 담당자는 같은 결정을 서로 다른 관점에서 검토하므로 충돌 지점을 숨기지 않고 결정권자를 명시한다.

## 국내 공고에서 확인한 범위

LINE Plus의 [Senior Cloud Security Engineer](https://careers.linecorp.com/ko/jobs/3052/)는 2026-08-07 게시 공고에서 AWS 표준 보안 아키텍처 수립과 개발·SRE 협업을 요구했고 7년 이상을 명시했다. 토스의 [Security Engineer (클라우드 보안)](https://toss.im/career/job-detail?job_id=6960856003)은 2026-10-09 확인 시 멀티 클라우드 보안 아키텍처 업무와 5년 이상 경험을 적었다. 두 공고는 클라우드 보안 직무에 아키텍처 책임이 포함된 사례이며 독립 '보안 아키텍트' 전체의 필수 연차는 아니다.

## 경력 확장과 면접 근거

시스템·클라우드·제품 보안에서 여러 팀의 변경을 설계 원칙으로 묶어 본 경험이 진입 기반이 될 수 있다. 포트폴리오에는 가상 서비스의 초기 설계, 두 개 이상의 통제 대안, 선택한 이유, 운영팀이 발견한 제약, 최종 결정 기록을 담는다. 면접에서는 유행하는 설계 이름보다 '어떤 위험을 얼마만큼 낮추고 어떤 업무 비용을 만들었나'를 설명한다. 구현자에게 불가능한 요구를 내리는 대신 검증 가능한 최소 기준과 단계적 개선을 합의한 경험이 중요하다.

## 지원 전에 확인할 질문

- 전사 보안 원칙을 정하는가, 특정 클라우드·제품의 설계 심의를 맡는가?
- 권고안을 거부하거나 예외를 승인할 권한은 어디에 있는가?
- 설계 결정 이후 구현 검증까지 참여하는가, 문서와 자문 단계에서 끝나는가?
- 운영 장애와 비용 제약을 함께 판단할 어떤 팀들이 회의에 참여하는가?

'아키텍트'라는 제목은 시니어 설계 책임을 뜻할 수 있지만 조직에 따라 실행 권한이 다르다. 지원자는 거대한 다이어그램보다 선택하지 않은 대안의 이유와 운영팀의 반대 의견을 어떻게 반영했는지 기록한 사례를 준비해야 한다.

## 근거와 확인 범위

공식 아키텍처 역할 자료와 인접 채용 공고를 함께 읽었다. 직함과 책임 범위는 조직 규모에 따라 달라지고, 클라우드 사례를 모든 산업의 표준 조직도로 일반화하지 않는다.
