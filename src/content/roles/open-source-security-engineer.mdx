## 직무의 목적과 두 업무 위치

오픈소스 보안은 **외부 구성요소를 사용하는 조직**과 **공개 프로젝트를 만드는 조직**에서 다르게 일한다. 사용 조직의 담당자는 어떤 구성요소가 어느 서비스에 들어갔는지 파악하고, 취약점·지원 종료·정책 변경이 알려지면 영향받는 제품과 수정 책임자를 찾는다. 공개 프로젝트의 담당자는 외부 제보를 받아 유지관리자와 수정 버전 배포(릴리스)·사용자 안내를 조율한다. 한 사람의 업무가 두 쪽을 모두 포함할 수는 있지만 두 위치의 권한과 고객은 같지 않다. 지원자는 공고의 대상이 **회사 내부의 사용 코드**인지 **프로젝트 자체의 배포물**인지 먼저 확인한다.

국내 직접 사례인 [토스뱅크의 Security Researcher (오픈소스 보안) 공고](https://toss.im/career/job-detail?job_id=7985037003)는 **사용 조직 쪽**이다. 사내 오픈소스 반입·배포 정책, 사용 현황과 [소프트웨어 자재명세서(SBOM)](/glossary/#softwarebillofmaterials), 구성요소 취약점의 조치 추적을 맡긴다. 이 포지션은 인프라·웹/모바일 취약점 진단도 함께 적고 지원자의 전문성에 따라 업무 비중을 조정한다고 안내한다. 공개 프로젝트의 제보 접수·수정 릴리스를 맡는 채용으로 바꾸어 읽을 수 없다.

공개 프로젝트 쪽의 업무를 이해하려면 [OpenSSF의 프로젝트 보안 기준](https://baseline.openssf.org/)과 [유지관리자용 취약점 공개 조정 안내](https://oss-vulnerability-guide.openssf.org/maintainer-guide.html)를 참고할 수 있다. 이 자료는 제보자·유지관리자·사용자 사이의 협의와 증거를 설명하지만 한국의 독립 채용 직함이나 입문 요건을 증명하지 않는다.

## 한 주의 업무 흐름

**사용 조직:** 개발팀이 새 구성요소를 반입하려 하면 실제 사용할 제품·버전, 사용 이유, 소유자와 업데이트 책임을 확인한다. 기존 구성요소에 취약점이 알려지면 도구의 경고만으로 영향이 확정됐다고 쓰지 않고, 실제 사용 위치·버전·노출 조건을 개발팀과 대조한다. 수정, 교체 또는 한시적 예외의 선택지를 제품 책임자에게 전달하고 배포 뒤 다시 확인할 증거와 날짜를 남긴다. [토스뱅크 공고](https://toss.im/career/job-detail?job_id=7985037003)처럼 반입 정책·SBOM 관리·구성요소 분석 도구(SCA)·개발 파이프라인 연동을 한 자리에 묶을 수도 있다. 도구 결과의 소유권과 최종 출시·위험 수용 권한은 실제 조직에서 확인해야 한다.

**공개 프로젝트:** 평상시에는 누가 비공개 제보를 읽고 답할지, 어떤 버전이 지원 대상이며 누가 릴리스를 승인하는지 유지관리자와 합의한다. 제보가 오면 영향 범위와 미확인 조건을 기록하고 수정 담당자·재검토자·배포 담당자와 일정을 조정한다. 사용자에게 안내할 수 있는 사실과 아직 비공개인 내용을 구분한다. 지원이 끝난 버전이나 담당자가 부재한 프로젝트라면 대체 연락과 지원 정책을 먼저 확인한다. 담당자가 혼자 수정 릴리스나 공개 날짜를 약속하지 않는다. 개발 절차 개선에는 [NIST SSDF](https://csrc.nist.gov/pubs/sp/800/218/final)를 참고할 수 있지만 지침을 따른다는 말만으로 프로젝트의 보안 상태를 보증할 수는 없다.

## 대표 산출물과 품질 기준

- **사용 조직의 구성요소·소유자 목록:** 어떤 제품과 버전에 무엇이 포함됐는지, 누가 변경할 수 있고 누가 고객 영향을 판단하는지 기록한다. 목록이 있다고 해서 모든 의존성의 안전을 보증하지 않는다.
- **사용 조직의 영향·조치 기록:** 경고의 출처, 실제 사용 여부, 영향받는 범위, 수정·교체·예외 결정과 재확인 결과를 연결한다. 보안 담당자의 권고와 제품 책임자의 출시·위험 수용 결정을 구분한다.
- **공개 프로젝트의 제보·릴리스 기록:** 접수 시점, 확인된 영향 버전, 미확인 조건, 수정·검토·배포 책임, 사용자 안내와 공개 결정의 근거를 연결한다. [OpenSSF 기준](https://baseline.openssf.org/)을 참고하되 프로젝트의 인력과 지원 범위에 맞는 절차를 만든다.

## 협업과 조직별 범위

사용 조직에서는 개발·제품팀이 실제 포함된 코드와 배포 시점을, [DevSecOps 엔지니어](/careers/devsecops-engineer/)가 반복 점검의 실행 조건을, 법무·조달 담당자가 사용 조건과 계약 쟁점을 제공할 수 있다. 오픈소스 보안 담당자는 도구의 경고를 제품별 영향과 실행 가능한 조치로 바꾸어 전달한다. 공개 프로젝트에서는 유지관리자가 코드·지원 버전과 릴리스 제약을 알고, 제보자와 배포판·기업 사용자가 각자의 영향 정보를 제공한다. 자원봉사자가 많은 프로젝트에 상용 제품팀의 일정·승인 구조를 그대로 가정하지 않는다. 두 환경 모두 다른 팀의 결정을 자신의 단독 승인으로 쓰지 않아야 한다.

## 진입과 성장

사용 조직 쪽에는 개발·제품 보안·DevSecOps·취약점 관리 경험에서 이동할 수 있다. 입문자는 자신이 소유한 예제 서비스의 구성요소 목록과 영향 검토를 연습할 수 있지만, [토스뱅크의 확인된 공고](https://toss.im/career/job-detail?job_id=7985037003)는 오픈소스 반입·활용 관리 **경험을 필수로 요구**한다. 가상 포트폴리오만으로 그 조건을 충족했다고 쓰지 않는다. 공개 프로젝트 쪽에서는 유지관리자와 보안 정책·지원 범위를 정리하고 공개 가능한 문서를 개선하는 기여가 출발점이 될 수 있다. 국내에서 그 업무만을 전담하는 독립 채용공고는 이번 조사에서 확보하지 못했으므로 공개 기여를 곧 취업 경로로 약속하지 않는다.

경력이 쌓이면 사용 조직에서는 여러 제품의 구성요소 위험과 배포·고객 안내를 조정하고, 공개 프로젝트에서는 여러 지원 버전과 사용자에게 미치는 영향을 판단할 수 있다. 두 일을 오갈 때에는 무엇을 사용·승인·배포할 권한이 있었는지 구분해 설명한다. 특정 프로그래밍 언어, 자격증, 공개 기여 횟수를 모든 채용의 공통 요건으로 제시할 근거는 없다.

## 포트폴리오 예시

**사용 조직을 목표로 한다면** 자신이 소유한 작은 예제 서비스에 외부 구성요소 세 가지를 넣고, 각 구성요소의 사용 위치·소유자·버전과 업데이트 책임을 정리한다. 한 구성요소에 문제가 알려졌다는 합성 상황을 만들어 실제 사용 여부, 영향이 확인된 범위, 개발팀에 묻거나 수정할 항목, 배포 뒤 재확인 시점을 한 장에 적는다. 스캔 결과나 구성요소 목록만 붙이지 않고 **어떤 제품 결정을 누가 내려야 하는지** 드러내야 한다.

**공개 프로젝트를 목표로 한다면** 가상의 라이브러리와 기여자·릴리스 담당자를 설정한다. 지원 버전과 비공개 제보 창구를 적은 정책 초안, 제보 확인 메모, 수정·공개 시점을 합의하기 위한 기록을 만든다. 구버전 사용자에게 새 버전을 바로 제공하지 못하는 경우에는 확인된 영향과 아직 약속할 수 없는 일을 분리한다. 면접에서는 어느 쪽 자료든 **확인한 사실, 다른 담당자에게 요청한 결정, 미확인 영역**을 표시한다. 가상 문서를 실무 경력이나 실제 제보 처리 성과처럼 소개하지 않는다.

## 지원 전에 확인할 조건

- 공개 프로젝트 자체의 제보·릴리스를 맡는가, 사내 제품이 사용하는 외부 구성요소의 위험을 관리하는가?
- 공고의 결과물이 보안 권고문·지원 버전 안내·릴리스 협의 기록인가, 아니면 사내 반입 심사·구성요소 목록·취약점 조치 기록인가? 두 쪽을 모두 맡는다면 업무 비중은 어떻게 나뉘는가?
- 사용 조직이라면 구성요소 사용 현황, 실제 취약점 영향, 수정·예외와 배포 후 확인을 누가 각각 책임지는가?
- 영향 버전, 수정 범위와 공개 시점을 누가 결정하며 담당자가 부재할 때 대체 연락 경로가 있는가?
- 지원 종료 버전과 하위 사용자에게 보내는 안내의 책임은 어느 팀에 있는가?
- 유지관리자가 상근 직원인지 자원봉사 기여자인지, 보안 담당자가 제안과 승인 중 어디까지 맡는가?

## 채용 근거와 한계

[토스뱅크의 Security Researcher (오픈소스 보안) 공고](https://toss.im/career/job-detail?job_id=7985037003)는 2026-10-25 공식 본문에서 확인한 정규직의 **사용 조직 쪽 직접 사례**다. 반입·배포 정책, SBOM, 구성요소 취약점의 추적과 개발 파이프라인 연동을 적고, 인프라·웹/모바일 진단도 같은 포지션에 포함한다. 오픈소스 반입·활용 관리 경험을 필수로 두며, 별도 최소 연차는 이 본문에서 확인되지 않는다. 이 공고가 공개 프로젝트의 비공개 제보·수정·릴리스 책임을 직접 증명하는 것은 아니다. 공개 프로젝트 전담 국내 공고는 이번 조사에서 확보하지 못했다.

[OpenSSF 프로젝트 보안 기준](https://baseline.openssf.org/)과 [유지관리자용 취약점 조정 안내](https://oss-vulnerability-guide.openssf.org/maintainer-guide.html)는 공개 프로젝트 업무의 참고자료다. 두 지침도 국내 채용 빈도, 독립 직함, 신입 가능성이나 연봉은 입증하지 않는다. 지원자는 공고에서 사용 조직의 구성요소 관리와 공개 프로젝트의 제보·릴리스 중 무엇을 실제로 맡는지 확인해야 한다.
