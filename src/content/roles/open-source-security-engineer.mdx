## 직무의 목적과 책임

오픈소스 보안 엔지니어는 공개 저장소를 가진 프로젝트와 그 사용자가 취약점과 배포 위험을 다룰 수 있게 돕는다. 공개 코드에는 기여자, 유지관리자, 외부 제보자, 배포판 제작자, 기업 사용자처럼 서로 다른 사람들이 참여한다. 따라서 이 직무의 중심은 문제를 혼자 찾아내는 능력만이 아니라, 비공개 제보부터 수정 검증, 릴리스, 사용자 안내까지 책임자와 시간을 맞추는 일이다. 어떤 조직은 프로젝트 자체의 보안을 전담하고, 어떤 조직은 여러 오픈소스 구성요소를 사용하는 제품팀에서 이 일을 겸한다. 이 페이지는 **프로젝트를 만들고 배포하는 쪽**의 책임을 중심으로 설명한다.

[OpenSSF의 오픈소스 프로젝트 보안 기준](https://baseline.openssf.org/)은 프로젝트 성숙도에 맞는 보안 통제와 증거를 정리한다. [OpenSSF의 취약점 공개 조정 안내](https://oss-vulnerability-guide.openssf.org/maintainer-guide.html)는 제보자와 프로젝트 담당자가 보고·수정·안내를 함께 조율하는 과정을 설명한다. 두 자료 모두 채용 직함을 정하는 목록은 아니다. 실제 팀에서는 AppSec, 제품 보안, 릴리스 엔지니어, 프로젝트 유지관리자가 업무를 나누어 맡을 수 있다.

## 한 주의 업무 흐름

평상시에는 유지관리자와 함께 누가 보안 제보를 읽고 답할 수 있는지, 어떤 릴리스가 지원 대상인지, 배포 담당자가 누구인지 확인한다. 저장소 권한이나 릴리스 절차가 바뀌면 기존 보안 약속이 여전히 지켜지는지 살핀다. 새로운 기여자가 늘어날 때에는 복잡한 규칙을 일방적으로 요구하기보다 프로젝트가 감당할 수 있는 검토·승인 흐름을 만들고 문서에 남긴다.

비공개 제보가 도착한 주에는 제보자에게 접수 사실을 알리고, 유지관리자와 영향 범위 및 확인 책임을 분리한다. 수정이 필요하면 해당 버전의 담당자, 재검토자, 릴리스 관리자와 일정을 조정한다. 이미 공개된 자료와 비공개 정보를 혼동하지 않도록 안내 문구를 검토하고, 사용자에게 가능한 대응을 언제 알릴지 합의한다. 다수의 프로젝트가 같은 구성요소를 사용한다면 하위 사용자에게 미치는 영향을 따로 확인한다. 개발 절차를 개선하는 활동에는 [NIST SSDF](https://csrc.nist.gov/pubs/sp/800/218/final)를 참고할 수 있으나, 지침을 따른다는 말만으로 실제 프로젝트의 보안 상태를 보증할 수는 없다.

## 독자가 확인할 대표 산출물

- **취약점 처리·공개 기록:** 제보 접수 시점, 확인된 영향 범위와 불확실성, 수정·검토·배포 책임, 제보자와 사용자에게 보낸 안내, 공개 결정의 근거를 연결한다. 아직 확인되지 않은 영향을 확정 표현으로 쓰지 않는다.
- **프로젝트 보안 운영 문서:** 제보 방법, 담당자 부재 시 대체 연락, 지원 버전 범위, 변경 승인 흐름, 릴리스 검증 증거를 짧고 찾기 쉽게 정리한다. [OpenSSF 기준](https://baseline.openssf.org/)을 참고하더라도 모든 항목을 기계적으로 통과시키기보다 프로젝트 규모와 유지관리 인력을 함께 기록한다.

## 협업과 조직별 범위

유지관리자는 코드와 릴리스의 현실적인 제약을 알고, 외부 연구자는 문제의 단서를 제공하며, 제품팀·배포판 담당자는 자신들이 쓰는 버전의 영향을 설명한다. 법무·대외 소통 담당자는 공개 문구와 약속이 조직의 책임과 일치하는지 검토할 수 있다. 엔지니어는 각자의 정보를 모아 빠진 결정을 보이게 한다. 오픈소스 프로젝트는 상근 인력이 없거나 자원봉사 기여자가 많을 수 있어, 상용 제품팀의 일정·권한 구조를 그대로 가정해서는 안 된다. 제보자의 기여를 인정하고 사용자에게 필요한 사실을 전달하는 태도도 중요한 업무 역량이다.

## 진입과 성장

입문 단계에서는 공개 프로젝트의 보안 정책과 지원 범위를 읽고, 제보·수정·공지의 기록을 정리하거나 보안 관련 문서를 개선하는 기여가 가능하다. 실제 취약점 제보를 연습 자료로 공개하거나 유지관리자의 승인 없이 민감한 내용을 게시하는 활동은 포트폴리오로 적절하지 않다. 개발·제품 보안·릴리스 운영 경험이 쌓이면 여러 버전과 하위 사용자의 영향을 판단하고, 프로젝트가 지속할 수 있는 공개·검증 절차를 설계한다. 특정 프로그래밍 언어, 자격증, 공개 기여 횟수를 모든 채용에 필요한 조건으로 제시할 근거는 없다.

## 포트폴리오 예시

가상의 공개 라이브러리를 설정하고 기여자 두 명과 릴리스 담당자 한 명이 있는 팀을 만든다. 지원 버전과 보안 제보 창구를 명시한 정책 초안, 제보가 들어왔을 때 담당자에게 보내는 비공개 확인 메모, 수정 여부와 공개 시점을 판단하기 위한 한 장의 기록을 작성한다. 이어서 구버전 사용자에게 수정 릴리스를 바로 제공하지 못하는 상황을 넣어 어떤 사실을 먼저 확인하고 누구와 일정을 협의할지 적는다. 공개 가능한 가상 자료만으로도 협업, 책임 배분, 사용자 안내의 품질을 보여줄 수 있다.

## 채용 근거와 한계

Open Home Foundation의 [Home Assistant Security Engineer](https://jobs.ashbyhq.com/openhomefoundation/c3089fc1-31ef-4cee-9ab0-68a94b1dfdb6) 공식 채용 페이지를 2026-10-09에 확인했다. 이 공고는 비공개 보안 제보 접수, 유지관리자와의 수정 조율, 릴리스·백포트, 프로젝트 빌드·배포 위험 개선, 오픈소스 커뮤니티 협업을 명시한다. 실제 제목은 **Security Engineer**이며 `Open Source Security Engineer`라는 독립 직함을 확인한 사례는 아니다. 이번 국내 공식 채용 표본에서는 오픈소스 프로젝트 보안을 전담하는 공고를 확보하지 못했다. 한 해외 프로젝트의 경력·거주 조건을 국내 시장이나 모든 오픈소스 보안 직무에 일반화하지 않는다.
