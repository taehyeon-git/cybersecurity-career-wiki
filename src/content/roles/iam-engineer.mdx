## 왜 필요한가

사용자가 퇴사해도 계정이 남거나 서비스 계정에 지나친 권한이 있으면 네트워크 통제가 강해도 위험이 지속된다. [IAM](/glossary/#identityandaccessmanagement) 엔지니어는 신원 확인과 자원별 권한 결정을 분리하고, 권한 부여·변경·회수의 전체 흐름을 운영한다. NIST Zero Trust는 네트워크 위치만으로 암묵적 신뢰를 주지 않는 자원 중심 접근을 설명한다.

## 업무 요청이 실제로 처리되는 방식

새 서비스 계정이나 직원 권한 요청이 오면 요청자의 업무 목적, 승인권자, 필요한 기간과 대상 자원을 확인한다. 퇴사·부서 이동·협력업체 계약 종료는 신규 권한 부여만큼 중요하다. IAM 담당자는 반복 요청을 자동화하더라도 예외가 남는 위치를 파악하고 권한 회수 결과를 확인한다. 인증 장애가 나면 접근을 전면 차단하거나 무조건 허용하는 단순 선택으로 끝나지 않는다. 서비스 연속성과 권한 오남용 가능성을 함께 보고 운영팀과 임시 절차를 합의한다.

## 남기는 문서와 협업

권한 설계 기록에는 사용자 유형, 수행 가능한 업무, 승인 절차, 최소 접근 범위, 만료 기준, 감사 기록과 소유자를 적는다. 접근 검토 자료에는 실제 사용 여부와 사용하지 않은 권한, 회수 계획, 미해결 예외의 승인자를 나눈다. 인사팀은 입사·이동·퇴사 사건을 제공하고 서비스 소유자는 업무 필요성을 확인한다. 보안 담당자는 통제 목표와 검토 주기를 정하지만 각 시스템의 업무 의미를 혼자 추정해서는 안 된다.

## 확인된 국내 채용 신호

토스의 [IT Security Specialist (신입 / 2년 이하)](https://toss.im/career/job-detail?job_id=8000384003)은 2026-10-09 확인 시 사내 기기·소프트웨어 운영과 계정·권한 관리를 현재 업무로 적고, IAM·MDM을 향후 성장 경로로 제시했다. 독립 IAM 엔지니어의 전체 업무와 동일시할 수 없다. LINE Plus의 [Senior Cloud Security Engineer](https://careers.linecorp.com/ko/jobs/3052/)는 2026-08-07 게시 공고에서 클라우드 IAM 통제 설계를 요구했다. 이는 클라우드 보안 직무 안에서 신원 관리가 수행되는 사례다.

[쿠팡의 Staff IAM Engineer 공고](https://www.coupang.jobs/kr/jobs/8172668/staff-iam-engineer-iam-architecture-governance/)는 IAM 직함의 **직접 채용 사례**다. 직원과 서비스 계정, 기계 신원, 접근 검토와 자동화를 함께 맡긴다. 2026-10-25 확인 당시 정규직·IAM 관련 **8년 이상**을 요구했고 2026-10-06 갱신, 마감일은 표시되지 않았다. 신입이 현재 맡는 계정 요청 처리와 Staff 수준의 전사 설계를 동일한 책임으로 보아서는 안 된다.

## 진입 경로와 면접 근거

IT 운영 경험은 계정 요청과 회수의 실제 흐름을 이해하는 강점이 된다. 다만 단순 요청 처리, 접근 정책 설계, 여러 서비스의 소유권 조정은 책임 수준이 다르므로 지원 공고의 범위를 확인한다. 면접에서는 자동화가 끝났다는 보고와 실제 권한 회수의 증거를 어떻게 구분했는지 말하고, 특정 공급자 자격증의 필수 여부는 공고에서 확인한다.

## 지원용 포트폴리오

### 사례 1: 접근 요청의 책임표

가상 조직의 고객지원·운영·개발팀이 같은 자료에 서로 다른 이유로 접근을 요청한다. 업무 목적, 허용 범위, 승인자, 정기 재검토자, 긴급 예외의 종료 조건을 표로 정리한다. 산출물에는 신청자가 이해할 안내와 감사 담당자가 나중에 확인할 증거를 함께 포함한다. 핵심은 정책 코드가 아니라 **필요한 업무와 과도한 접근의 경계**를 설명하는 능력이다.

### 사례 2: 조직 이동 시 인계 기록

팀 이동이나 퇴사 뒤 남은 접근을 어떻게 확인할지 가상의 인사·IT·보안 조직 간 책임을 그린다. 완료 신호와 실패 시 연락 경로, 수동 처리할 예외, 사후 재확인 날짜를 적는다. 면접에서는 자동화가 끝났다는 보고와 실제 접근이 회수됐다는 증거를 어떻게 구분할지 설명한다.

## 지원 전에 확인할 질문

- 사내 직원 계정, 고객 로그인, 클라우드 서비스 계정 중 주 대상은 무엇인가?
- 신청·승인·회수 절차의 정책을 설계하는가, 도구 운영과 요청 처리에 집중하는가?
- 긴급 접근과 장기 예외는 누가 승인하고 언제 다시 검토하는가?
- 인사·IT·서비스 소유자와 계정 생명주기 사건을 어떻게 연결하는가?

기기 관리와 계정 운영이 함께 있는 입문 공고를 독립 IAM 설계 직무와 혼동하면 준비 방향이 어긋난다. 실제 권한 모델을 바꿀 권한이 있는지, 단순 처리 업무인지 확인하고 본인의 포트폴리오도 그 책임 수준에 맞춰 제시한다.

## 근거와 확인 범위

쿠팡 Staff IAM 공고는 독립 직함의 직접 사례이고, 토스·LINE Plus 공고는 IAM이 더 넓은 직무에 포함된 인접 사례다. 세 공고의 경력 단계와 현재 업무를 나누어 읽어야 한다. Staff 공고 한 건으로 일률적인 진입 연차나 제품 자격을 요구하지 않는다.
