## 왜 필요한가

클라우드 제공자가 기반 시설을 보호해도 고객의 데이터, 권한, 서비스 설정은 사용 방식에 따라 위험해질 수 있다. 책임 범위는 서비스 모델과 제공자마다 다르므로 해당 서비스의 공식 문서를 확인해야 한다. 클라우드 보안 엔지니어는 계정과 워크로드가 늘어나도 통제가 일관되게 적용되도록 설계한다.

## 실제 수행 업무

- **입력:** 계정·구독·프로젝트 구조, 자산 목록, IAM 정책, 네트워크 경로, 로그·설정 결과.
- **과정:** 데이터와 관리자 경로를 파악해 최소 권한과 분리 경계를 설계한다. 설정 변경을 코드와 정책으로 검증하고 탐지 로그가 실제 남는지 확인한다.
- **출력:** 적용 가능한 기준 구성, 위반과 예외 내역, 수정 우선순위, 재검증 결과.

## 가상 실무 시나리오

**가상 시나리오:** 새 개발 환경의 저장소가 인터넷에 공개되어 있다는 경보가 나온다. 엔지니어는 테스트 계정에서 실제 익명 접근 가능 여부와 저장 데이터의 민감도를 확인한다. 버킷 정책을 수정하고 배포 코드의 기본값도 변경한다. 이후 감사 로그와 자동 점검으로 같은 설정이 다시 생기는지 확인한다.

## 업무에서 쓰는 역량과 도구

클라우드 콘솔은 현재 상태를 확인하고, 코드형 인프라는 기준 설정을 재현하며, 구성 점검기는 드리프트 후보를 찾는다. 자동 점검 결과는 실제 접근 경로와 사업 맥락으로 검증한다. [AWS Well-Architected Security Pillar](https://docs.aws.amazon.com/wellarchitected/latest/security-pillar/welcome.html), [Microsoft Cloud Adoption Framework 보안](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/secure/ready), [Google Cloud 보안 개요](https://docs.cloud.google.com/docs/security/overview/whitepaper)를 서비스별 기준으로 참고한다.

## 신입 준비

‘클라우드 보안’, ‘인프라 보안’, ‘플랫폼 보안’의 범위는 조직마다 다르다. 무료 또는 로컬 실습에서 비용 한도와 삭제 계획을 세운 뒤 IAM·네트워크·로그의 전후 상태를 보여준다. 제공자 자격증은 학습 경로일 수 있지만 실제 설정 검증을 대체하지 않는다.

## 포트폴리오 작업 예시

### 프로젝트 1: 최소 권한 스토리지

- **목표·선수 지식·환경:** 익명·과도한 접근을 막는다. IAM·네트워크 기초와 격리된 실습 계정이 필요하다.
- **작업·검증:** 소유자·읽기 전용·익명 접근 시나리오를 정의하고 정책 변경 전후 실제 요청을 테스트한다.
- **산출물·완료 기준·포트폴리오:** 정책 코드와 접근 행렬을 제출한다. 허용 요청은 유지되고 금지 요청은 거부되면 완료다.

### 프로젝트 2: 구성 드리프트 감지

- **목표·선수 지식·환경:** 보안 기준에서 벗어난 변경을 발견한다. 코드형 인프라 기초가 필요하다.
- **작업·검증:** 로그 활성화·공개 접근 금지 기준을 만들고 의도적 위반을 넣어 점검 결과를 비교한다.
- **산출물·완료 기준·포트폴리오:** 위반 로그, 수정 커밋, 재점검을 공개한다. 자동 점검과 실제 접근 시험이 일치하면 완료다.

## 한 주의 업무는 어떻게 흘러가는가

클라우드 계정과 서비스의 변경 요청이 들어오면 누가 어떤 데이터와 리소스에 접근하는지, 기존 기준에서 무엇이 달라지는지 확인한다. 자동 점검에서 나온 경고는 중요 자산 여부와 실제 노출 경로를 확인해 담당 팀에 전달한다. 반복되는 예외는 개별 티켓을 닫는 데 그치지 않고 표준 구성이나 배포 절차가 원인인지 살핀다. 신규 서비스의 보안 요구와 운영 환경의 이탈을 같이 다뤄야 하므로 개발자·플랫폼 운영자와 정기적으로 우선순위를 맞춘다.

## 남겨야 할 결과물

설정 오류 티켓에는 대상 계정, 소유 팀, 위험을 만든 변경, 확인 시각, 수정 기한과 재점검 결과가 있어야 한다. 아키텍처 검토 기록에는 허용할 접근 경로와 금지할 경로, 운영 책임자, 모니터링 방법, 예외 승인자를 나누어 쓴다. '기준 준수'라는 한 줄 결론만으로는 다음 배포에서 같은 실수가 반복된다. 재사용할 수 있는 기준과 자동 점검의 적용 범위를 남기는 것이 운영 성과다.

## 진입과 경력 이동

클라우드 운영이나 플랫폼 엔지니어링 경험에서 옮겨온다면 자신이 관리하던 계정·네트워크·배포 변경의 소유권과 사고 처리를 설명하는 것이 출발점이다. 포트폴리오에는 가상 조직의 두 서비스에 대한 접근 기준, 위반을 발견한 기록, 예외 처리와 재점검 증거를 포함한다. 면접에서는 특정 제품 버튼을 아는지보다 '사업상 필요한 연결을 유지하면서 과도한 권한을 어떻게 줄였나', '서비스 중단 위험과 보안 수정 일정을 어떻게 조정했나'를 말할 수 있어야 한다. 대규모 설계 책임은 운영 경험과 협업 기록을 쌓아 확장한다.

## 지원 전에 확인할 질문

- 계정과 네트워크의 기준을 직접 설계하는가, 운영팀의 설정을 점검하는가?
- 클라우드 제공자가 한 곳인지 여러 곳인지, 온프레미스와의 연결도 맡는가?
- 경보와 설정 오류를 발견했을 때 수정 권한과 장애 책임은 어느 팀에 있는가?
- 신규 서비스 출시 심의와 기존 계정의 상시 운영 중 어느 쪽이 더 많은가?

공고의 서비스 이름 목록만으로 업무를 판단하기 어렵다. 어느 규모의 자산에 어떤 결정권을 갖는지와 개발·SRE·인프라 팀의 분업을 물어야 준비 경험을 정확하게 대응시킬 수 있다. 경력 공고의 연차가 모든 조직의 진입 기준은 아니다.

## 근거와 확인 범위

공식 기준과 위 공고는 역할 범위를 파악하는 자료다. 클라우드 제공자, 사내 플랫폼팀의 권한, 규제 환경에 따라 실제 담당 범위가 달라진다. 공고가 바뀔 수 있으므로 게시·확인 시점의 사례로 읽는다.
