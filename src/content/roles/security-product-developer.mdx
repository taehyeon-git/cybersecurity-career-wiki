## 직무의 목적과 책임

보안 제품 개발자는 다른 조직의 위험을 줄이거나 운영을 돕는 소프트웨어를 만든다. 보안팀 내부에서 도구를 사용하는 사람과 달리, 제품의 사용자 요구, 설치·업데이트, 호환성, 장애와 지원 가능성까지 고려한다. 고객이 실제 환경에서 사용할 수 있도록 기능을 구현하고, 출시 뒤 발견된 결함을 버전별로 추적한다. 제품 종류가 엔드포인트, 네트워크, 신원, 데이터, 보안 분석 등으로 넓어 하나의 기술 목록이 모든 채용에 해당하지는 않는다.

개발자가 보안 문제를 이해해야 한다는 사실과 사용자의 시스템 보안을 단독 책임진다는 주장은 다르다. 기능 요구를 제품 관리자와 합의하고, 품질 담당자와 실패 조건을 정의하며, 제품 보안 엔지니어와 자신의 제품 자체가 공격 표면이 되는 문제를 검토한다. [NIST SSDF](https://csrc.nist.gov/pubs/sp/800/218/final)는 개발 과정에서 고려할 실무의 틀이지만 특정 제품 개발자 직함의 채용 조건은 아니다.

## 일하는 흐름

한 주는 고객 지원·제품 관리자·운영팀에서 들어온 사용 사례를 확인하는 것으로 시작할 수 있다. 요청이 실제로 어떤 문제를 해결하는지, 어떤 버전과 환경에 영향을 주는지 정리하고 완료 조건을 합의한다. 구현 단계에서는 기존 기능에 미칠 영향을 검토하고, 동료 리뷰와 제품 검증을 거친다. 결함이 발견되면 재현 가능성, 고객 영향, 임시 조치, 수정 버전과 안내 문구를 분리해 기록한다.

릴리스 직전에는 새 기능을 소개하는 말보다 적용 대상·알려진 한계·되돌릴 방법을 정확하게 전달하는 일이 중요하다. 출시 후에도 고객이 실제로 설치할 수 없는 수정이라면 효과가 제한되므로 운영·지원팀과 배포 일정을 조정한다. 한 개발자가 영업, 지원, QA, 보안 검토의 모든 최종 결정을 대신하지는 않는다.

## 대표 산출물

- **기능 명세와 검증 기록:** 사용자 문제, 지원 환경, 정상·실패 조건, 기존 버전과의 차이, 검증 결과를 연결한다. 구현과 요구가 왜 달라졌는지도 남긴다.
- **결함 수정·릴리스 기록:** 영향을 받는 버전과 사용 조건, 고객 안내 수준, 수정과 검증 상태, 배포 일정의 근거를 담는다. 미확인 영향은 확정적으로 표시하지 않는다.

## 협업과 조직별 범위

제품 관리자는 고객의 요구와 우선순위를 정리하고, QA 담당자는 실패 사례와 출시 판단 근거를 제공하며, 고객 지원팀은 실제 환경의 제약을 전한다. 제품 보안 담당자는 제품 자체의 취약점과 공개 절차를 검토한다. 작은 업체에서는 개발자가 여러 일을 겸할 수 있지만, 큰 업체에서는 제품군·플랫폼별로 전문화된다. 어느 구조가 보편적이라고 주장할 근거는 현재 없다.

## 진입과 성장

소프트웨어 개발 경험에서 출발해 보안 제품의 목적과 고객 업무를 배우는 경로가 가능하다. 초반에는 작은 변경의 요구와 테스트 결과를 명확히 남기고, 경험이 쌓이면 여러 버전과 고객 환경의 영향, 안정적인 배포, 긴급 수정의 우선순위를 책임진다. 시니어 개발자는 기능을 얼마나 빠르게 만들었는지뿐 아니라 잘못된 요구를 일찍 발견하고 여러 팀의 결정을 도왔는지도 설명해야 한다. 특정 언어나 자격증을 모든 보안 제품 개발의 필수로 제시하지 않는다.

## 포트폴리오 예시

가상의 보안 제품 기능을 하나 정해 사용자 문제와 운영 조건을 먼저 한 장으로 쓴다. 기능 구현 기록에는 사용자가 기대하는 결과, 실패했을 때의 안내, 이전 버전과의 차이, 검증 범위를 포함한다. 별도로 고객 제보 한 건이 들어왔다는 상황을 만들고 재현 질문, 영향 범위, 수정 우선순위, 릴리스 안내 초안을 작성한다. 면접에서는 기술 선택 자체보다 고객 문제와 출시 판단을 어떻게 연결했는지 설명한다.

## 지원 전에 확인할 업무 조건

- **제품과 배포 방식:** 고객 환경에 설치하는 제품인지 서비스 형태로 제공하는 제품인지 확인한다. 배포 방법에 따라 이전 버전 지원, 장애 복구, 고객과의 소통에서 개발자가 맡는 범위가 달라질 수 있다.
- **개발과 유지보수의 비중:** 신규 기능, 고객별 호환성, 긴급 결함 수정 중 무엇이 주 업무인지 묻는다. 공고의 언어·도구 목록보다 실제 제품군과 지원 버전이 업무를 더 잘 설명할 때가 많다.
- **출시 뒤 책임:** 수정이 고객에게 적용됐는지 누가 확인하고, 지원팀이 재현하지 못한 문제를 개발팀이 어떻게 넘겨받는지 확인한다. 코드를 합쳤다는 사실과 고객 문제의 종료는 같지 않다.

초기 지원자는 작은 기능의 **사용자 요구, 실패 조건, 수정 전후 검증**을 한 묶음으로 보여줄 수 있다. 경력 지원자는 여러 버전이 공존하는 상황에서 수정 범위와 출시 순서를 결정한 사례를 익명화해 설명한다. 어떤 경우든 고객에게 약속한 동작과 실제 검증한 범위를 구분하는 태도가 중요하다.
