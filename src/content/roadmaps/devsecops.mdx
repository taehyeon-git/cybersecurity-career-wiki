# DevSecOps 커리어 경로

DevSecOps는 하나의 도구나 자격증 이름이 아니다. 개발과 배포 흐름에서 보안 검토가 지속되도록 책임과 피드백을 설계하는 일에 가깝다. 이 안내는 검사 기능을 구현하는 기술 강좌가 아니라 어떤 팀에서 누가 정책을 정하고, 경고를 처리하고, 예외를 승인하는지 이해한 뒤 자신의 경험을 지원 자료로 만드는 과정이다.

## 목표 직무를 정하기

데브섹옵스 엔지니어가 독립 보안팀에 있을 수도 있고, AppSec 담당자나 플랫폼 엔지니어의 업무에 포함될 수도 있다. 먼저 공고에서 검사 정책의 소유, 파이프라인 변경 권한, 개발팀 지원, 배포 장애 대응 중 어디에 책임이 있는지 표시한다. 개발팀의 코드 수정까지 요구하는지, 보안팀은 기준과 우선순위만 정하는지도 확인한다. 같은 자동화 경험이라도 제품 수십 개를 지원하는 플랫폼 조직과 단일 서비스 개발 조직에서는 협업 방식이 다르다.

개발 경력이 있다면 실제 배포 병목을 줄인 경험을, 플랫폼 운영 경력이 있다면 실패 복구와 권한 관리의 경험을 출발점으로 삼을 수 있다. 보안 진단 경험에서 옮겨온다면 발견 결과를 개발자가 처리할 수 있는 흐름으로 바꾼 사례가 필요하다. 어느 출발점이든 자신의 변경이 다른 팀의 시간을 어떻게 바꿨는지 설명해야 한다.

## 공고에서 확인된 업무와 한계

LINE Plus의 [Senior Cloud Security Engineer](https://careers.linecorp.com/ko/jobs/3052/)는 2026-08-07 게시 공고에서 개발·SRE 조직과 DevSecOps 협업을 요구했다. 토스의 [Security Researcher (모바일보안)](https://toss.im/career/job-detail?job_id=7780944003)은 2026-10-09 확인 시 모바일 점검을 CI/CD에 통합하는 업무를 적었다. 두 사례 모두 DevSecOps 활동을 포함하지만 독립 'DevSecOps Engineer' 직함이 아니다. 채용명과 업무를 동일시하지 말고, 실제 공고에서 서비스 소유자와 보안 결과의 처리 책임을 묻는다. 경력·사용 제품도 해당 회사의 맥락에 한정된다.

## 포트폴리오는 운영 흐름을 보여준다

허가된 예제 저장소를 대상으로 검사 경고가 발생한 상황을 설정한다. 한 장의 운영 설계서에 경고가 어디로 전달되는지, 누가 사실 여부를 확인하는지, 출시를 멈출 기준과 예외 승인권자는 누구인지 적는다. 처리 기록에는 발견 시각, 담당자, 수정 또는 예외 결정, 만료일과 재검토 결과를 둔다. 이어서 일부 경고가 오탐이었다는 피드백을 받고 기준을 바꾼 이유를 기록한다. 실행 화면만 붙이면 기능 시연으로 끝나지만, 사람과 결정의 흐름을 적으면 직무 수행의 증거가 된다.

## 피드백과 개선

개발자 역할의 사람에게 경고 문구만 보고 어떤 행동을 해야 하는지 묻고, 플랫폼 담당자 역할의 사람에게 규칙 때문에 배포 장애가 났을 때 되돌리는 절차가 분명한지 확인한다. 의견이 갈리면 누구의 위험 판단이 필요한지 기록한다. 포트폴리오에는 처음 설계와 피드백 후 설계를 둘 다 남겨 협업에 따라 기준을 바꾼 과정을 보여준다. 실제 고객의 비공개 파이프라인이나 보안 경고를 공개하지 않는다.

## 지원서와 면접에서 말할 것

지원서에는 'SAST 구축'처럼 기능 이름만 적지 말고 경고 처리 시간, 개발팀과 합의한 차단 기준, 만료된 예외를 다시 확인한 결과를 설명한다. 면접에서는 제품팀이 검사 지연을 문제 삼을 때 어떤 자료로 우선순위를 조정할지, 오탐이 많아 검사가 무시되면 무엇부터 바꿀지를 질문받을 수 있다. 특정 도구를 쓰지 않았더라도 책임·피드백 구조를 설계한 경험을 정확히 설명할 수 있다. 반대로 도구 운영만 해봤다면 정책 결정까지 맡았다고 과장하지 않는다.

## 지원 전 점검표

- 검사의 정책 소유, 자동화 구현, 경고 분류와 수정 중 내가 보여줄 수 있는 책임이 무엇인지 나눈다.
- 공고가 보안팀의 자문 역할인지 플랫폼팀의 운영 역할인지, 배포 실패 때 당직이나 복구 책임이 있는지 확인한다.
- 포트폴리오의 경고 처리 표에 사람·기한·예외 승인·재검토 결과가 실제로 연결되어 있는지 본다.
- 개발자 피드백을 받고 기준을 바꾼 사례를 준비하고, 차단을 늘린 것만 성과로 주장하지 않는다.
- 회사별 제품 이름이 다를 때도 같은 운영 결정을 설명할 수 있는 문장으로 경험을 고친다.

기술 기능을 많이 나열했는데도 이 항목에 답하기 어렵다면 준비가 부족한 곳은 도구 설치가 아니라 협업과 소유권 기록일 수 있다. 가상 실습의 한계와 직접 운영한 범위도 지원서에 분명히 적는다.

## 이 경로의 한계

독립 직함의 국내 공고 표본이 충분하지 않다. DevSecOps는 공식 NICE에서 역량 영역으로도 사용되며 회사별 업무 이름은 다르다. 이 경로는 채용 가능성이나 필수 연차를 보증하지 않는다. 지원할 때는 공고의 배포 권한, 운영 당직, 개발 협업 범위를 다시 확인한다.
