# 애플리케이션 보안 커리어 경로

이 경로는 웹 기술을 순서대로 가르치는 강좌가 아니다. 애플리케이션 보안 직무에서 어떤 결정을 내리고 누구에게 어떤 결과물을 전달하는지 파악한 뒤, 자신의 경험을 채용 근거로 정리하기 위한 안내다. 학위나 자격증 목록보다 일의 범위와 설명 가능한 산출물을 먼저 확인한다.

## 목표 직무와 조직 위치 고르기

애플리케이션 보안 엔지니어는 새 기능의 설계·코드·출시 위험을 개발팀과 검토하는 경우가 많다. 제품 보안 엔지니어는 출시 후 제보, 영향받는 버전, 수정 릴리스와 고객 안내까지 이어 맡을 수 있다. 두 직함은 회사마다 겹치므로 직함만 보고 진로를 정하지 않는다. 공고에서 출시 전 평가, 안전한 개발 지원, 외부 취약점 접수, 고객 영향 판단 가운데 어떤 결과에 책임지는지 표시한다. 보안팀이 직접 수정을 하는지 개발자가 수정하고 보안팀이 재검증하는지도 확인한다.

개발 경험이 있다면 기능의 요구사항을 분석하고 수정안을 동료와 합의한 사례를 출발점으로 삼는다. 진단 경험이 있다면 결함을 발견한 뒤 개발자가 실제로 고칠 수 있게 설명했는지 살핀다. 두 경우 모두 고객 데이터나 이전 회사의 비공개 코드를 전시하지 않는다.

## 공고를 읽어 업무의 크기 확인하기

2026-10-09 확인한 토스의 [Security Researcher (모의해킹/취약점 분석)](https://toss.im/career/job-detail?job_id=4076085003)은 웹·모바일·API·내부 시스템 평가와 위협 모델링, 수정 권고를 한 포지션에 묶었다. [Security Researcher (모바일보안)](https://toss.im/career/job-detail?job_id=7780944003)은 모바일 취약점 점검과 개발·배포 과정의 보안 통합을 요구했다. 실제 공고명은 이 경로의 직무명과 다르며 모바일 전문성과 일반 AppSec를 하나의 필수 요건으로 합칠 수 없다. 관심 공고를 세 개 정도 모아 대상 서비스, 주 책임, 협업팀, 경력 조건을 별도 칸에 적고 공통점보다 차이를 먼저 본다.

## 포트폴리오는 업무 의사결정의 묶음으로

자신이 소유하거나 허가받은 예제 서비스에서 새 기능을 출시한다고 가정한다. 한 페이지의 검토 범위서에 사용자 역할, 영향받는 데이터, 개발 일정과 검토 질문을 적는다. 발견 사항 기록에는 문제의 재현 조건, 실제 업무 영향, 수정 책임자, 임시 대안과 재검증 결과를 나눈다. 제품 보안 쪽을 목표로 한다면 동일한 사례에 영향을 받는 버전 표와 고객지원용 짧은 안내문을 붙인다. 코드나 검사 도구가 아니라 문제의 발견에서 수정 확인까지 누가 무엇을 결정했는지가 핵심이다.

초안은 개발자 역할의 동료가 읽고 실제로 수정할 수 있는지, 제품 담당자 역할의 사람이 출시 판단을 할 수 있는지 피드백을 받는다. 이해되지 않은 용어와 누락된 전제 조건을 수정 이력에 남긴다. 완벽한 첫 결과보다 피드백을 받아 문서를 바꾼 증거가 협업 역량을 더 잘 보여준다.

## 지원서와 면접에서 설명할 것

지원서에는 '취약점 분석 가능' 대신 검토 대상, 자신의 역할, 제안한 조치, 수용 여부와 후속 결과를 한 문장씩 적는다. 면접에서는 왜 그 문제를 먼저 다뤘는지, 출시 일정과 위험이 충돌했을 때 어떤 선택지를 제시했는지, 수정 후 무엇을 다시 확인했는지 설명한다. 경험이 부족하면 실제 직무를 수행했다고 과장하지 말고 가상 사례임을 명시한다. 공고가 요구한 제품·고객 환경을 자신의 예제와 억지로 동일시하지 않는다.

## 지원 전 점검표

- 지원하려는 팀이 신규 기능 설계 검토, 취약점 진단, 출시 후 제보 처리 중 무엇을 주 업무로 삼는지 공고 본문에서 표시한다.
- 개발팀이 수정할 때 내가 직접 판단한 부분과 개발자·제품 담당자가 결정한 부분을 포트폴리오에서 분리한다.
- 결과물 한 건에 검토 범위, 위험의 업무 영향, 수정 담당자와 재검증 날짜가 모두 있는지 확인한다.
- 서류에 적은 검사 도구의 이름보다 그 결과 때문에 어떤 출시·수정 결정이 달라졌는지 말할 수 있는지 점검한다.
- 공개 자료에 고객 데이터, 이전 회사의 코드, 허가되지 않은 서비스의 진단 기록이 들어가지 않았는지 다시 검토한다.

이 다섯 항목이 비어 있다면 기술 목록을 더 늘리기보다 이미 한 작업의 책임과 후속 결과를 다시 정리한다. 어느 제품과 어떤 개발 조직을 지원할지에 따라 필요한 경험은 달라지므로 공고마다 서류를 새로 맞춘다.

## 연결되는 전문 역할

모바일 보안 담당자는 같은 서비스 평가라도 단말과 앱 배포의 제약을 더 가까이 다루고, 오픈소스 보안 담당자는 외부 구성요소의 제보·수정·공개 조정을 깊게 맡을 수 있다. 데브섹옵스 엔지니어는 검토 결과가 개발·배포 과정에 반복 가능하게 들어가도록 돕는다. 웹 모의침투 테스터와 취약점 연구원은 발견과 재현에 강점을 가질 수 있지만 제품팀의 출시 판단이나 수정 완료를 혼자 책임진다고 가정하지 않는다. 이 경로를 인접 출발점으로 쓰되 공고의 실제 소유권에 맞춰 포트폴리오를 고른다.

## 이 경로의 한계

AppSec는 회사의 제품 형태와 개발 조직에 따라 설계 자문, 직접 진단, 취약점 접수 중 비중이 바뀐다. 위 국내 공고는 접근 가능한 일부 표본이며 시장 전체의 필수 경력이나 채용 규모를 말하지 않는다. 출처의 개발 관행은 업무 판단을 돕지만 특정 공고의 채용 조건을 대신하지 않는다.
