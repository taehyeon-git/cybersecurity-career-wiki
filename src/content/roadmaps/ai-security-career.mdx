AI 서비스 보안은 새 유행어를 나열하는 일이 아니라 제품이 AI 기능을 어디에 쓰고, 실패가 누구에게 어떤 영향을 주며, 그 위험을 출시 전후에 누가 확인하는지 결정하는 일이다. 이 경로는 **AI 시스템과 서비스 자체를 보호하는 업무**를 중심에 둔다. AI를 다른 보안 업무에 활용하는 자리도 같은 ‘AI 보안’이라는 말을 쓸 수 있으므로, 지원자는 직함보다 책임 산출물을 읽어야 한다. 아래 준비 방법은 확인 가능한 직무 프레임워크와 제품 개발 지침을 바탕으로 한다.

## 지금 경험에서 시작하는 순서

- **무경험 시작:** 먼저 [보안 직무 탐색·진입 경로](/roadmaps/cybersecurity-fundamentals/)에서 공고의 주 책임을 읽는 연습을 한다. 공개 가능한 가상 AI 기능 하나를 골라 사용자, 잘못된 결과가 주는 영향, 사람이 다시 확인해야 할 지점을 한 장에 적는다. 이 자료는 업무 이해의 증거이지 실제 서비스 평가 경력이 아니다. 아래 SK쉴더스 공고에는 경험 요건의 상충이 있어 무경험 지원 가능성을 확정할 수 없다.
- **관련 경력 전환:** [애플리케이션 보안 엔지니어](/careers/application-security-engineer/)라면 개발팀과 수정·재검증을 조정한 기록을, [제품 보안 엔지니어](/careers/product-security-engineer/)라면 출시와 고객 영향 판단을, 데이터·ML 개발자라면 품질 평가와 배포 변경을 다룬 기록을 골라 **AI 기능 평가 계획·결과·미확인 범위**로 다시 쓴다. 이전 경험을 모델 보안 전문 경력으로 바꿔 적지 않는다.
- **시니어 확장:** 여러 제품의 평가 기준과 책임 경계를 조정해 본 사람은 [AI 보안 엔지니어](/careers/ai-security-engineer/)와 [보안 아키텍트](/careers/security-architect/)의 역할 문서를 읽고 공통 평가 기준, 제품팀의 수정 책임, 잔여 위험 승인자를 한 장의 의사결정 기록에 연결한다. 전사 기준을 만든 적이 없다면 검토에 참여한 범위만 밝힌다. 한 회사의 경력 공고가 모든 조직의 필수 승진 단계는 아니다.

## 어떤 팀에서 무엇을 결정하는가

AI 보안 엔지니어는 제품팀에게 AI 기능의 사용 목적, 대상 사용자, 입력되는 정보와 출력의 사용 방식을 묻는다. 평가 담당자와 함께 실패로 볼 상황을 정의하고, 관찰 결과와 추정한 위험을 나눈다. 개발·데이터 팀은 제품 동작과 수정 가능 범위를 설명하고, 개인정보 담당자는 데이터 처리와 이용자 고지의 쟁점을 검토한다. 보안 아키텍트는 여러 서비스에 공통으로 필요한 설계 기준을 조정할 수 있다. 이 경로를 선택할 때 공고가 모델 평가, 서비스 통합, 보안 업무 자동화, 고객 환경 구축 중 어디에 있는지 먼저 표시해야 한다.

[NICE](https://www.nist.gov/itl/applied-cybersecurity/nice/nice-framework-resource-center/resources/occupations-jobs-and-work)는 [업무 역할](/glossary/#niceworkrole)과 실제 채용 직함의 차이를 설명한다. 처음부터 전담 직함을 얻어야만 이 분야의 일을 배울 수 있는 것은 아니지만, 포트폴리오만으로 채용 자격을 충족한다고 주장할 수도 없다.

## 공고를 세부 분야로 읽기

2026-10-25 확인한 [SK쉴더스 EQST Lab의 AI 보안 연구원 공고](https://www.skshieldusapply.com/ko/o/240272)는 생성형 AI·AI Agent 시스템의 보안·안전성 평가와 평가 기준 연구를 직접 명시한다. AI를 기존 취약점 분석에 활용하는 업무도 함께 있다. 판교 근무의 `정규직(경력)`으로 표시됐지만, 헤더의 `경력 무관`과 본문의 정보보안 실무 또는 동등 연구·취약점 연구 경험 요구가 다르다. 헤더의 **2026-10-28 23:59 마감**과 본문의 `채용 시 마감`도 서로 맞지 않는다. 따라서 입문자 허용 여부와 실제 마감은 지원 전에 다시 확인해야 한다.

과거 기록한 NAVER Cloud AI Security 상세 URL은 채용 목록으로 이동했고, 삼성서울병원 AI 보안담당 상세 URL은 브라우저에서 `존재하지 않는 페이지`로 표시됐다. 이 두 공고의 당시 업무와 경력 조건을 **현행 지원 기준**으로 사용하지 않는다. 공고를 읽을 때 실제 제품이 AI를 쓰는지, 사내 AI 사용을 통제하는지, 보안 업무에 AI를 도입하는지를 먼저 표시하고 모집의 필수·우대 조건을 나누어 읽는다.

지원자가 읽을 표에는 제품 또는 서비스 대상, 평가할 실패 상황, 재현·수정 책임, 고객 접점, 요구된 선행 경험을 별도 칸으로 둔다. 'LLM', 'AI 레드팀', '가드레일'이라는 단어가 있다는 이유로 모든 업무를 공격 시험으로 판단하지 않는다. 어떤 조직은 제품팀의 출시 판단을 돕고, 다른 조직은 평가 체계를 만들거나 고객 환경의 제약을 해결한다. 기술명은 이 차이를 찾기 위한 단서일 뿐 커리어의 목표가 아니다.

## 포트폴리오: 사용 사례에서 출시 의견까지

직접 만든 작은 AI 기능이나 공개 예제를 고르고 **제품 사용 사례 한 장**을 작성한다. 어떤 사용자가 어떤 결정을 돕기 위해 결과를 읽는지, 잘못된 결과가 단순 불편인지 더 큰 피해인지, 사람의 재확인이 어디에 있는지 적는다. 실제 개인 정보나 기업 내부 자료를 넣지 않는다. 두 번째 산출물은 **평가 계획과 결과 기록**이다. 실패로 볼 상황 두세 가지, 확인한 조건, 관찰된 결과, 확인하지 못한 영역을 분리한다. 정확한 수치가 없으면 점수를 만들어내지 않는다. 수정 후에는 같은 조건에서 다시 확인하고 새 문제가 생겼는지 기록한다.

세 번째로 짧은 **출시 판단 메모**를 만든다. 제품팀이 결정해야 할 선택지, 남은 위험, 이용자 안내가 필요한 부분, 출시 뒤 관찰할 신호와 재검토 시점을 적는다. 보안 담당자가 출시를 혼자 승인했다고 쓰지 않는다. 개발자 역할의 동료에게 수정 요청이 이해되는지, 제품 담당자 역할의 사람에게 남은 위험이 의사결정에 충분한지 피드백을 받는다. 초안과 수정본의 차이를 남기면 기술 도구보다 협업과 판단의 과정을 보여줄 수 있다. [NIST SSDF](https://csrc.nist.gov/pubs/sp/800/218/final)와 [OWASP GenAI Security Project](https://genai.owasp.org/)는 검토 질문을 찾는 공식 참고 자료로 사용할 수 있으나 내용을 그대로 복사해 일반적인 위험 목록만 제출하지 않는다.

## 지원서와 면접

지원서에는 'AI 보안에 관심'이라는 말보다 평가한 사용 사례, 자신의 역할, 확인한 실패 조건, 제안한 개선, 재평가 결과를 적는다. 개발 배경 지원자는 보안 문제를 제품 영향으로 설명한 과정을, 보안 배경 지원자는 모델·데이터 팀의 제약을 듣고 평가 범위를 조정한 과정을 보여준다. 면접에서는 발견 사실과 재현되지 않은 우려를 구분하고, 일정 때문에 모든 평가를 마치지 못했을 때 무엇을 우선 확인할지 설명한다. 이전 회사의 비공개 모델·데이터를 예시로 공개하지 않는다.

## 지원 전 점검과 한계

- 공고가 'AI for Security'인지 'Security for AI'인지, 또는 두 분야의 협업인지 업무 본문에서 표시한다.
- 책임 산출물이 모델 평가 결과, 제품 보호 요구, 보안 자동화 기능, 고객 구축 기록 가운데 무엇인지 확인한다.
- 포트폴리오의 관찰 결과와 예상 위험, 자신의 결정과 제품팀의 최종 결정을 분리한다.
- 가상 사례를 실제 서비스 출시 경험처럼 적지 않고 원본 데이터의 공개 가능성을 점검한다.
- 단일 기업의 경력 조건을 업계 전체의 필수 연수·학위·자격으로 확대하지 않는다.

SK쉴더스의 직접 공고 한 건으로 AI 서비스 보안 직무의 국내 채용 빈도나 초급 포지션 규모를 말할 수 없다. [NICE](https://www.nist.gov/itl/applied-cybersecurity/nice/nice-framework-resource-center/nice-framework-current-versions)와 OWASP 자료도 채용 규모의 근거는 아니다. 새 공고를 읽을 때는 모델·서비스 검토, 사내 AI 사용 운영, 고객 지원 중 어떤 책임이 중심인지와 필수·우대 조건을 따로 표시한다.
