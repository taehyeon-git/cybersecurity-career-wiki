# 소프트웨어 구성요소 분석

## 정의와 범위 · 먼저 이해하기

직접·간접 의존성과 알려진 취약점, 라이선스, 유지 상태를 살펴보는 활동. 이 문서의 주제는 여러 직무에서 함께 사용하는 지식이며, 특정 채용 직무 하나와 동일하지 않다.

## 왜 필요한가

애플리케이션은 외부 패키지와 그 하위 의존성에 의존한다. 자체 코드만 검사하면 이미 알려진 구성요소 문제와 업데이트 필요성을 놓친다.

## 핵심 개념과 구성 요소

잠금 파일, 패키지 버전, 전이 의존성, 취약점 식별자, 수정 버전과 영향 조건을 구분한다. 발견 정보가 곧 해당 서비스에서 악용 가능하다는 뜻은 아니다.

## 기본 작동 원리

빌드에서 실제 사용한 패키지 목록을 추출하고 공개 취약점 정보와 대조한다. 노출 여부, 실행 경로, 보완 통제, 수정 가능성을 검토해 담당자와 기한을 정한다.

## 작은 예시

직접 사용하는 라이브러리는 안전해 보여도 하위 패키지에 취약점이 있을 수 있다. 잠금 파일을 바꾼 뒤 기능·보안 회귀 테스트까지 실행한다.

## 위험과 한계

패키지 이름과 버전 매칭에는 오류가 있을 수 있고 취약점 데이터는 게시·분석 시차가 있다. 패치가 없을 때는 영향을 검토하고 완화책을 기록한다.

## 실제 보안 업무에서의 활용

DevSecOps는 빌드 중 의존성 가시성을 제공하고 AppSec은 실제 코드 경로와 영향도를 판단한다. 제품 보안은 업데이트 정책과 공급자 위험을 연결한다.

## 선행 학습과 관련 기술

선행 주제: **프로그래밍과 스크립팅, 안전한 개발 수명주기**. 관련 주제: **소프트웨어 자재 명세서, 취약점 관리, CI/CD 보안**. 이 연결은 학습을 위한 제안이며, 회사마다 직무의 업무 범위는 달라질 수 있다.
